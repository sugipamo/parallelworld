# 確率的知識とLeanによる形式的同一性の意味論

設計仕様 v0.4 — 対象を任意のファイルに広げた叩き台

実走の記録：Claude Code（claude-opus-5-5）のワーカー2体を並列に動かし、主張・証拠・接続・Leanの証明が共有ログに記録されることを確認した（§8）。

v0.1 の原則はそのまま残す。

> 知識からLean命題への接続は仮説であり、Lean命題間の証明された関係は確定的である。
> 証明の確実性は接続の不確実性を消去せず、接続の不確実性は証明の確実性を損なわない。

v0.2 で「どう計算するか」と「数値をどこから持ってくるか」を変え、v0.3 で各部分を既存の数学概念の名前どおりに組み直した。記号での定式化と概念への対応は [symbols.md](symbols.md) にある。変更点はすべて §2 に理由つきで並べた。

## 1. 構成

```
Orchestrator        pw/orchestrator.py   タスクごとに git worktree を切り Claude Code を並列起動
  └ Worker × N      claude -p --model claude-opus-5-5
        │ MCP (stdio)   pw/mcp_server.py
        ▼
Knowledge Kernel    pw/kernel.py         追記専用イベントログ (SQLite)、信頼性モデル
  ├ 形式層          pw/lindenbaum.py     検証済みの関係で表示されたブール代数、合同閉包
  ├ 確率層          pw/credal.py         クレーダル集合、一般化ベイズ則、コピュラ
  └ Lean Gate       pw/lean_gate.py      固定された Γ のもとで証明を検証
```

ワーカーは状態を直接書かない。MCPツール経由でイベントを追記するだけ。

形式的な主張の登録（`Kernel.claim_formal`）はオーケストレーターが行う。タスクの必須の主張を `{subject, type, predicate, gloss}` で書き、Γ の定義は `--lean-dir` で指すLeanプロジェクトの `Gamma.lean` に置く。

証拠の撤回（`Kernel.retract`）もMCPに出していない。検査の仕組みの誤りを正すための操作で、オーケストレーター側が理由つきで行う。

## 2. v0.1 からの変更

1〜7 が v0.2、8〜16 が v0.3、17〜20 が v0.4。

| # | v0.1 | v0.2 | 理由 |
|---|------|------|------|
| 1 | 結合分布 μ を保持する | 分布は持たない。`infer` は区間 `[lo, hi]` を返す | Ω は命題数に対して指数的。述べられていない依存は「未知」のまま残し、幅として見せる |
| 2 | `ground(H, F, prior)`、`observe(e, likelihood)` | 事前確率と尤度はカタログから引く。エージェントは数値を渡せない | エージェントが数値を言えば、それは主観的確信度の保存になる |
| 3 | 証明は F₁ ↔ F₂ のみ | `holds` / `not` / `iff` / `implies` / `contradiction` | 並列作業では衝突（矛盾）の検出が同値性と同じくらい要る |
| 4 | 証明の追加も確率状態の変化 | 証明は Ω の絞り込み。ベイズ更新ではない | Leanの定理は「最初から不可能だった世界」を消す。経験的証拠と同じ更新にすると事前確率と衝突する |
| 5 | 証拠の依存は結合確率で表す | 同一出自は同一証拠。それ以外は依存のクラスの中で区間をとる（→9）。独立は理由つきで宣言する | 結合確率そのものは誰も与えられない |
| 6 | 証拠はエージェントが報告 | テスト等は Kernel が自分で実行して記録する | 自己申告は証拠の出自を曖昧にする |
| 7 | 状態変化は2種類 | 3種類：モデル拡張 / 証拠 / 証明 | `ground` と独立性宣言はどちらでもない |
| 8 | 同一性は F₁ ↔ F₂ | 主張を「仕様 P」と「対象 a」に分け、同じ仕様（`pred_iff`）と同じ対象（`obj_eq`）を別々に証明する | 定理はすべて互いに同値なので、証明済みの命題どうしの ↔ は何も言わない |
| 9 | （v0.2）証拠の依存は「重複〜独立」の独自の混合 | コピュラのクラスを名前で選ぶ：`independent` / `comonotone` / `pqd`（既定）/ `frechet` | 独自の混合に根拠がなかった。`frechet` が v0.1 の文字どおりの読み |
| 11 | 接続仮説 G は一つ | 「述語が主張の性質を表す」G と「対象がコードを表す」M に分ける。M は同じコード・同じ対象についての主張すべてが共有し、Kernel が実コードと突き合わせて証拠を作る | 一つにまとめると、同じコードについての主張の間の依存が見えない |
| 12 | モデルの検査が一致する確率は 0.97 | モデルの仮説は全称命題なので、正しければ一致は確実（確率 1）。不一致 1 件で反証 | 1 未満だと、検査を重ねるほど下界が下がる |
| 16 | モデルの検査はエージェントが書いたコマンドで行う | モデルの仮説に、定義域・呼び出し方・出力の比べ方を記録し、検査は Kernel が組み立てる | 「何が一致していると主張しているか」がコマンド文字列の中に埋まっていた。証拠の同一性も、著者の書き方に依存していた |
| 17 | 決定の対象はコード | 対象は任意のファイル、またはその中の箇所（Markdown の節、JSON のキー、Python の定義）。箇所の内容のハッシュで版を決める | 設定、スキーマ、文書も決定の対象になる。ファイル全体のハッシュだと、無関係な編集で読みが失効する |
| 18 | モデルは「コードの振る舞いを表す項」 | 接続は「読み」：この箇所のこの内容は、この Lean の項として読める。得方は 3 通り（変換式が計算する／呼び出して突き合わせる／誰かが述べる） | コードでない対象には「振る舞い」がない。共通なのは、内容を項として読むこと |
| 19 | 決定は確立したら終わり | 決定は立ち続け、ファイルが変わるたびに当て直す。機械的にできる分は `pw.check`、読み直しは `pw.maintain`、残りが人 | 管理の仕事は、読みを更新して決定がまだ成り立つかを確かめ続けることに落ちる |
| 20 | 決定は「この箇所はこの仕様を満たす」 | それに加えて「事実」：一つの事柄と、それを述べている箇所の一覧。決定は、全部の箇所が同じ値として読めること。正解の値は決定の側に書かない | 同じことが文書・設定・コードの複数箇所に書かれ、片方だけ変わるのが、実際に起きる食い違い。値を決定に書くと、変えるたびに決定も書き直すことになる |
| 13 | 検査の入力はエージェントが選ぶ | Kernel が入力を無作為に引く検査（`sample_model`）を追加。検査は交換可能になり、一致が増えるほど下界が上がる | 人が選んだ入力の間の依存は未知で、何件一致しても 1 件ぶんの支持にしかならない |
| 14 | 主張は自然言語の文 | 必須の主張は「コードが述語を満たす」として述語で与えられる（`claim_formal`）。述語は Γ の定義を使ってよい | 文から述語への翻訳がなければ、仕様の仮説 G そのものが要らない。G は片側が自然言語なので、検査で確かめる手段がない |
| 15 | G への証拠は逆翻訳の自己申告 | 自然言語のまま残る主張では、述語に反例があること（空虚でない）と、別々の著者が同じ仕様に結んだことを、形式層から読み取って証拠にする | どちらも Lean が確かめた事実で、言語モデルの判断に頼らない |
| 10 | 意味的同一性は確率 | 距離 d(A, B) = 1 − P(A ↔ B) として問い合わせる | 形式的同一性（d = 0）と接続（d ≤ 1 − P(G)）が同じ物差しに乗り、v0.1 §6 は三角不等式になる |

## 3. モデル

原子命題は3種類。

- **H** 知識命題。自然言語の文（同じ文面は同じH）か、形式的な主張「コード s は述語 P を満たす」。
- **F** Lean命題。閉じた命題そのもの、または述語 P : A → Prop を対象 a : A に当てた P(a)。等しいと証明されたFは一つの類にまとめ、一つの原子として扱う。P₁ = P₂ かつ a₁ = a₂ なら P₁(a₁) と P₂(a₂) も同じ類になる（合同閉包）。
- **G** 仕様の仮説。「述語 P は主張の言う性質を表す」。主張ごと。
- **M** 読みの仮説。「この対象の、この内容は、Lean の項 a として読める」。対象はファイル、またはその中の箇所で、内容のハッシュつきで識別する。内容が変われば別の仮説になり、同じファイルの他の箇所が変わっても影響しない。読みの得方は 3 通りで、それも仮説の一部として記録する。
  - **変換式**が内容から項を計算する。仮説は「変換式が正しい」に縮む。
  - 対象が呼び出せるコードなら、**定義域と呼び出し方**を述べる。仮説は「定義域のすべての入力で、呼び出した結果が a の値に等しい」で、Kernel が無作為な入力で突き合わせる。
  - それ以外は、エージェントか人が項を**述べる**。機械的に確かめる手段はなく、支えは人の確認か、対象そのものへの検査だけ。
  主張をまたいで共有する：同じ対象・同じ項・同じ得方なら、誰が述べても同じ仮説。

接続の意味は `(G ∧ M) → (H ↔ F)`。閉じた命題への接続は G だけ、形式的な主張の接続は M だけを持つ。

可能世界は、質問に現れる原子とそこから接続・証明でつながる原子（連結成分）の真偽割り当て。Leanの定理に反する世界は最初から除く。
Leanが真偽を決めたFは定数なので、それを共有しているだけでは連結とみなさない。別々の連結成分は互いに影響しない。

事前分布は次の線形制約を満たす分布すべて。一つに決めない。

- `P(G) = π_G`、`P(M) = π_M`。G と M の間の依存は置かない。
- G・M のどの真偽の組でも `P(F | その組) = π_F`（同値性以外の証明に現れないFについて）。
- Hのどの接続も成り立たない G・M の真偽の組のそれぞれで `P(H | その組) = π_H`。

これは証言の信頼性モデルで、2つ目と3つ目が「信頼性と事実は独立」「信頼できない報告は基準率の抽選」にあたる。これがないと、`ground` しただけでHの確率が広がり、Mを支持する証拠がHの下界を下げる。

証拠は対象原子の真偽だけに依存する尤度 `[P(e|真), P(e|偽)]` を持つ。同じ対象への証拠は、独立が宣言されない限り一つのブロックに入り、ブロックの同時尤度は選んだコピュラのクラスが許す範囲をとる。既定の `pqd` は正の依存で、独立と完全な重複の間。

`infer(φ)` は、上の制約と両端の尤度のもとで `P(φ | 証拠)` の最小と最大を線形計画で解く。

### 数値例（テスト済み）

| 状況 | 結果 |
|------|------|
| π_G₁=0.9, π_G₂=0.8, `F₁ ↔ F₂` を証明 | `P(G₁∧G₂) ∈ [0.7, 0.8]`、`P(H₁↔H₂) ∈ [0.7, 1]`（v0.1 §6） |
| π_G=0.9, π_H=0.5, `F` を証明 | `P(H) = 0.95`、`P(G) = 0.9` のまま（条件3） |
| π_G=0.8, π_M=0.75, `F` を証明 | `P(G∧M) ∈ [0.55, 0.75]`、`P(H) ∈ [0.775, 0.875]` |
| 同じMを共有する2つの主張。Mの検査が1件一致 | 両方の主張の下界が上がる |
| 人が選んだ入力でMの検査が 1 件 / 5 件一致（π_M=0.75） | 下界はどちらも 0.896。下がらないが上がりもしない |
| 無作為に引いた入力で 1 件 / 5 件 / 20 件一致 | 下界 0.857 / 0.947 / 0.984 |
| 検査が 1 件でも不一致 | `P(M) = 0`。主張は基準率に戻る |
| 形式的な主張。π_M=0.75、`F` を証明 | `P(H) = 0.875` の一点（未知の依存がない） |
| 自然言語の主張で、述語に反例を示す（π_G=0.8） | `P(G) = 0.851`。反例を足しても変わらない |
| 尤度 0.9/0.15 の証拠を別々の実行で2件 | `pqd` で `P(H) ∈ [0.844, 0.976]`、`frechet` で `[0.842, 1]`。独立を宣言すると 0.973 |
| 同じ実行を2体が報告 | 1件として扱う。変化なし |
| 同じHへの2つの形式化が Lean上で矛盾 | `Conflict` を返す |
| 証明済みのF₁、F₂の間に `iff` を追加 | 各Hの区間は変わらない |
| 同じ仕様（`pred_iff`）だが対象が別 | 命題は別の類のまま。`P(H₁↔H₂) ∈ [0, 1]` |
| さらに対象も等しい（`obj_eq`） | 命題が同じ類になり `P(H₁↔H₂) ≥ 0.7`、距離 `≤ 0.3` |

## 4. 操作（MCPツール）

| ツール | 内容 |
|--------|------|
| `claim(text)` | Hを登録 |
| `model(h, object, setup, call, domains)` | 形式的な主張に、コードのモデルを付ける。呼び出し方と各引数の定義域も述べる。Mだけを導入 |
| `reject_object(p, object, proof)` | 述語 p を満たさない対象を示し、`¬ p(object)` を証明する。述語が空虚でない証拠 |
| `read_place(h, place, object, quote)` | 事実の箇所の一つが何と言っているかを、根拠の一文つきで述べる。比較は Kernel がする |
| `ground_at(h, subject, type, predicate, object, setup, call, domains)` | 「コード subject のモデル object が仕様 predicate を満たす」としてG・M・F・P・Oを導入 |
| `sample_model(m, n)` | Kernelが M に記録された定義域から入力を引き、記録された呼び出し方でコードを呼んで、Leanでの値と比べる。Mを支持するための検査 |
| `check_model(m, values)` | 指定した入力（定義域の値）で同じ比較をする。Mを反証するための検査 |
| `ground(h, lean)` | 閉じた命題としてGとFを導入 |
| `observe_command(target, kind, command)` | Kernelがコマンドを実行し、成否を証拠として記録。出自は「コマンド＋作業ツリーの状態」 |
| `observe(target, kind, outcome, source)` | コマンドで作れない証拠（レビュー、逆翻訳） |
| `declare_independent(eid, justification)` | 証拠を独立として扱う宣言 |
| `prove(relation, args, proof)` | Lean Gateに証明を提出。失敗は証拠にしない。関係は `holds` `not` `iff` `implies` `contradiction` `pred_iff` `pred_implies` `obj_eq` `pred_disjoint` `pred_rejects` |
| `infer(query)` | 原子の論理式に対する `[lo, hi]` |
| `distance(a, b)` | 二つの主張・命題が食い違う確率の区間 |
| `status()` | 全主張の区間と接続先、命題・仕様・対象の類、受理済み証明 |

## 5. Lean Gate

- 定理の文面はGateが登録済みのF文面から書く。エージェントが渡すのはタクティクだけ。
- 検証はLeanを2回走らせる。1回目で文面とタクティクを含むモジュールをコンパイルし、2回目はエージェントの文字列を一切含まないファイルからそれを import して `#print axioms` する。
- 受理条件：1回目が成功し、2回目の出力が公理レポート1行だけで、許可リスト（`propext`、`Classical.choice`、`Quot.sound`）に収まる。
- 2回に分ける理由：タクティクは任意のメッセージを出力できる。1ファイルで済ませていた初版は、`trace` で偽の公理レポートを出すと `1 = 2` の「証明」を受理した。
- Γ ＝ ツールチェーン＋`lean/Gamma.lean`＋許可リスト。Gateは実行中のLeanのバージョンが `lean-toolchain` と一致しなければ何も受理しない。証明イベントにΓのハッシュを記録する。

## 6. 正しさの条件（v0.1 §9 との対応）

1. 意味論の統一 — H・F・Gは同じ世界の上の原子。事実と仮説の区別はない。
2. 証明の健全性 — 証明イベントはGate経由でしか書けない。
3. 接続の不確実性 — 証明はGの確率を変えない（テスト済み）。
4. 依存性の保存 — 同一出自は重複排除、それ以外は宣言まで区間。`dependence="frechet"` なら依存について何も仮定しない。
5. 確率的整合性 — 区間は制約を満たす分布全体の上の最小と最大。

## 7. 未解決

- **Γ の定義が意図どおりかは、このシステムの外。** 形式的な主張は仕様の仮説を消すが、溝は「定義が意図どおりか」に移る。Γ を変更するレビューがその確認の場になる。
- **無作為な検査の入力分布が仮置き。** 引数ごとに 0〜15 の一様分布。支持されるのは「この分布のもとでほぼ確実に一致」までで、稀な入力でだけ食い違うモデルは見つからない。誤ったモデルの一致率の事前分布（平均 0.5、集中度 2 以上）も仮置き。
- **仮説どうしの依存が未知のまま。** G と M は同じエージェントが同時に書くので正に依存していそうだが、何も置いていない。その分 `P(G∧M)` はフレシェ区間になる。
- **作業ツリーの同一性が粗い。** 証拠の出自は「コマンド＋ `git status` と `git diff`」で決めている。無視されていないキャッシュが生成されると別の出自に見える。
- **対象の等しさは全域でしか言えない。** `clamp` と `bound` は lo ≤ hi の範囲では同じ値を返すが、`obj_eq` は全域での等しさを要求するので証明できない。定義域つきの等しさが要る。
- **カタログの数値は仮置き。** 主張・接続・モデルの基準率と、テストやレビューの尤度には較正データがまだない。事実と箇所の読み（§10）はこの数値を使わず、規則の表と読み手の測定で判定する。
- **証拠が接続を通じて他の原子の区間を広げる。** G同士の事前の相関が未知なので、G₁への証拠がG₂の下界を少し下げることがある（dilation）。
- **関係（`implies` / `contradiction` / `pred_implies` 由来の含意）に現れるFには事前確率を置いていない。** 置くと含意が同値に化けるため。その分、区間が広い。
- **基準率と証明が両立しないとき `Conflict` で止まる。** 事前確率を緩める規則が要るかもしれない。
- **Gateの入力検査は禁止語リスト。** 新しいコマンドや構文定義の混入を語の一致で弾いているだけで、原理的な保証ではない。
- **連結成分が14原子を超えると解けない。** 分割か近似が要る。
- **コードそのものはLeanの外にある。** Fはコードのモデルに関する命題で、不確実性の大半はGに残る。
- **Γが変わったとき、古い証明をどう扱うか未定義。**

## 8. 実走の記録

### 1回目（v0.2）

2体のワーカーに、同じ仕様の関数を別々の方法で実装させた（`clamp` は min/max、`bound` は if/else）。約36秒で両方が完了した。

- それぞれが主張を登録し、Kernelにテストを実行させ、Lean命題に接続し、証明を通した。
- `bound` 側は `status` で相手のFを見つけ、2つのFの `iff` も証明した。
- 判定は当初 `[0.890, 0.958]` で閾値0.9に届かず保留になった。原因は `iff` の追加で2つの主張が一つの連結成分になり、接続仮説どうしの未知の相関が区間を広げたこと。証明済みの命題どうしの同値は情報を持たないので、これは実装の誤りだった。
- 修正後、同じログから各主張は 0.905 になる（テスト1件＋証明、接続の事前確率0.6）。

### 2回目（v0.3）

同じ2つのタスクを、述語と対象を分けた道具で流し直した。

- 2体は相談なしに、一字一句同じ述語 `fun f => ∀ x lo hi : Nat, lo ≤ hi → lo ≤ f x lo hi ∧ f x lo hi ≤ hi` を書いた。文面が同じなので、証明なしで同じ仕様 `P:811a001185` になった。
- 対象は別々（min/max と if/else）で、命題も別の類のまま。
- `bound` 側は `status` で相手の対象を見て、「lo > hi では値が違う（x=0, lo=5, hi=3 で 5 と 3）」と反例を挙げ、`obj_eq` を試みなかった。
- 判定は両方 0.905 で閾値 0.9 を超えた。

つまり「同じ仕様を、別の対象が満たしている」と記録された。1回目に空虚な同値として現れたものが、意味のある形で分かれた。

### 3回目（仕様の仮説とモデルの仮説を分離）

同じ2つのタスクを流し直した。

- 各ワーカーは `ground_at` でコード（`clamp.py::clamp`、`bound.py::bound`、どちらもファイル内容のハッシュつき）を指定し、仕様の仮説 G とモデルの仮説 M が別々に記録された。
- 各ワーカーは `check_model` を5回ずつ呼び、Leanの対象と実コードの出力が5件とも一致した。どちらも、主張の範囲外である lo > hi の入力を1件含めていた。
- `bound` 側は、その範囲外の検査結果（`bound(5, 7, 3)` が 7）を根拠に、`clamp` とは別の対象だと判断して `obj_eq` を試みなかった。
- 判定は両方 `[0.917, 1.000]` で閾値 0.9 を超えた。モデルの仮説は `[0.905, 0.999]`。

このとき、既定の `pqd` では依存する検査を重ねると尤度比の下限が下がった。モデルの仮説だけで見ると、一致1件での下界は 0.893、5件では 0.880。原因は「正しいモデルでも一致する確率は 0.97」という尤度の置き方で、変更 12・13 で直した。

### 4回目（演繹的な検査と無作為な検査）

同じ2つのタスクを流し直した。

- 各ワーカーは `sample_model` で 30 件ずつ無作為な検査を行い、すべて一致した。加えて `check_model` で境界値（lo > hi を含む）を 1〜2 件試し、これも一致した。
- モデルの仮説の下界は 0.905 から 0.992 に上がった。
- 主張の判定は両方 `[0.937, 1.000]`（3回目は 0.917）。

主張の下界を抑えているのは、もうモデルの仮説ではなく仕様の仮説 G（基準率 0.8、証拠なし）になった。G への証拠（逆翻訳など）を Kernel が自分で作る手段はまだない。

### 5回目（形式的な主張）

必須の主張を述語で与えた。`Spec.Bounded` を実走用の Γ に定義し、タスクには「`clamp.py::clamp` は `Spec.Bounded` を満たす」と書いた。`bound` 側には、自分の言葉で主張を一つ立てることも求めた。

- 必須の主張には仕様の仮説が作られず、接続はモデルの仮説だけになった。判定は `[0.998, 1.000]` と `[0.997, 1.000]`（4回目は 0.937）。
- `bound` 側が自分で立てた主張「lo ≤ x ≤ hi なら x をそのまま返す」は自然言語のままなので、仕様の仮説が付いた。ワーカーは「常に lo を返す関数はこの述語を満たさない」ことを証明し、述語が空虚でないことを示した。仕様の仮説の下界は 0.847、主張は `[0.952, 1.000]`。
- この主張と必須の主張は同じコードについてのものなので、同じモデルの仮説を共有した。モデルの検査 30 件は両方の主張を支えている。
- 2つの必須の主張は同じ仕様 `Spec.Bounded` を指し、対象は別。`bound` 側は今回も反例 (5, 7, 3) を挙げて、対象が等しいとは主張しなかった。

## 9. 時間をまたぐ決定

管理の仕事は一つのループになる。決定は「このファイルはこの仕様を満たす」、接続は「このハッシュのファイルはこの Lean の項として読める」。ファイルが変わるたびに、読みを更新し、決定がまだ成り立つかを確かめる。

| ファイルの読み方 | 変わったときに起きること | 要るもの |
|------------------|--------------------------|----------|
| 変換式（`reader`）が項を計算する | 再計算して、保存してある証明を当て直す | なし（`pw.check`） |
| コードのモデルと呼び出し方 | 同じ項を新しいコードに無作為な検査で突き合わせる | なし（`pw.check`） |
| エージェントが述べる | 読みが失効する | エージェントの読み直し（`pw.maintain`） |

それでも残るもの（Lean が否定を証明した違反、決定どうしの矛盾、誰も確かめていない読み）だけが人に回る。対象はコードに限らない（`experiments/artifacts/RESULTS.md`）。

形式的な主張は、コードの版をまたいで立ち続ける「決定」として扱う。

- **証拠は版に結びつく。** モデルの仮説 M はファイル内容のハッシュつきのコードに、テストの結果は作業ツリーに結びつく。`infer(..., current=, tree=)` は、いまの版についての証拠だけを数える。コードについての主張は「いまのコード」についてのものなので、これは `pw.check` だけでなく、オーケストレーターのマージ判定（各タスクのブランチのコード）とワーカーへの `infer` / `status`（そのワーカーの作業ツリーのコード）でも同じ。別の版のモデルを混ぜると、反証されたものと支持されたものが打ち消し合って区間が広がる。
- **当て直し（`python -m pw.check`）。** 立っている決定それぞれについて、コードが変わっていれば同じ Lean の対象を新しい版に付け直し、保存してある無作為な検査とテストを再実行する。結果は「現行」「再確立」「違反」「証明の対象外」「失効」「裏付けなし」。言語モデルは使わない。
- **決定どうしの矛盾。** `pred_disjoint` で 2 つの仕様が両立しないと証明されると、同じコードについてのその 2 つの決定は同時に成り立たない（`¬(H₁ ∧ H₂)`、モデルを経由しない）。`pw.check` は矛盾として報告し、人がどちらかを取り下げる（`Kernel.withdraw`）まで終了コード 1 を返す。
- **基準率のとり方。** 裏付けのない主張の基準率は、「それを排除する決定が成り立たない世界の中で」とる。そうしないと、確立済みの決定と矛盾する提案が一つあるだけで全体が評価不能になる。

- **自然言語の主張の当て直し。** 形式的でない主張は、記録されたコマンドを再実行して確かめる。状態は「検査が通る」「検査が落ちる」で、下界は判定に使わない。
- **形式化の注記。** `ground` / `ground_at` は、著者が「落としたもの」「足したもの」を書いた注記を接続と一緒に保存する。数値は動かさない。

- **証明の保存。** 受理された証明の本文を記録し、読みが変わったら同じ手順を新しい命題に試す。通れば再確立。同じ手順が否定を証明すれば「違反」。
- **人の確認。** 読み（モデルの仮説や仕様の仮説）を人が実物と見比べたことを、証拠として記録できる（`Kernel.sign_off`）。読みが変われば効果は残らない。

当て直しの状態「証明の対象外」は、コードが証明の対象だったモデルと一致しなくなったことを意味する。決定が破られたとは限らない。

実走の記録は `experiments/decisions/RESULTS.md` と `experiments/selfcheck/RESULTS.md` の追記。自然言語の決定についての知見は [natural-language.md](natural-language.md)。

## 10. 事実と箇所

プロジェクトの「事実」を、リポジトリ直下の `pw-facts.json` に列挙する。事実は一つの事柄（既定値、許可リスト、上限、名前の一覧など）で、それを述べている箇所を全部挙げる。

```json
{"name": "default dependence class", "type": "String",
 "places": ["docs/spec.md::3. モデル",
            {"at": "pw/kernel.py::Kernel.__init__", "read": {"find": "dependence=\"(\\w+)\"", "as": "string"}}]}
```

- 箇所は `path` か `path::箇所`。読み方（`read`）を付けた箇所は Kernel が読む。付けない箇所はエージェントか人が読む（`read_place`）。
- 読み方は宣言で書く。式は書けない。

  | キー | 意味 |
  |------|------|
  | `find` | グループを 1 つ持つ正規表現。箇所の中でちょうど 1 回一致しなければならず、グループの中身が値になる |
  | `find_all` | 同じ形で、一致を全部とって一覧にする |
  | `as` | 値の種類：`string`、`nat`、`int`、`permille`（小数を千分率の自然数に。割り切れなければ失敗） |
  | `sort` / `unique` | 一覧を並べ替える（文字列はコードポイント順、数は大きさ順）／重複を除く |

  何も評価しないので、同じ宣言はどの実装でも同じ意味になる。正規表現は主要な処理系に共通する範囲に限る（先読み・後読み、後方参照、名前つきグループは不可。`^` と `$` は行頭・行末）。
- 事実の同一性は名前と型で決まる。箇所の一覧や読み方を変えても同じ事実のままで、それまでの読みと人の確認は引き継がれる。
- 決定は「全部の箇所が同じ値として読める」。どの箇所も特別扱いしない。食い違ったとき、どれが正しいかは人が決める。
- 値を変えるときは、全部の箇所を変える。決定を書き直す必要はない。
- 意味論上は、各箇所の読みが仮説 M で、全部の読みが正しければ「主張 ⇔ 読みどうしの等式」。等式は Kernel が自分で Lean に通す。
- エージェントが読むときは、根拠の一文（その箇所にある、それを言っている文や表の行）を付ける。Kernel はそれが箇所に一字一句あることを確かめ、人が確認するときに見せる。単一の値の読みは、根拠の一文が残っているかぎり有効。一覧の読みは箇所全体に依存するので、箇所が変われば読み直す。
### 読みが成り立つ条件

- 読みが成り立つかどうかは、確率ではなく**規則の表**で決める（`pw-rules.json`。置かなければ `pw/rules.json` の既定）。表は「次の条件がそろえば成り立つ」という行の並びで、どれか 1 行を満たせばよい。

  | このリポジトリの規則 | 意味 |
  |------|------|
  | `computed` | 宣言された読み方で計算した読み |
  | `confirmed by a person` | 人が文面と見比べた |
  | `blind` ＋ `words occur in the place` ＋ `agrees with a computed place` | 目隠しの読み手が読み、値が文面にそのままあり、計算した箇所と同じ値 |
  | `blind` ＋ `words occur in the place` ＋ `read the same by a second model` | 上の 3 つ目の代わりに、別のモデルも目隠しで同じ値を読んだ |

  規則に使える条件は次の 7 つで、どれも Kernel が記録とファイルから判定する。

  | 条件 | 中身 |
  |------|------|
  | `computed` | その箇所に読み方（`pattern`、`reader`）が宣言されている |
  | `confirmed by a person` | 人の確認が記録にある |
  | `blind` | 測定済みの読み手が、その箇所の本文だけを渡されて読んだ |
  | `words occur in the place` | 読んだ値が、根拠の一文（一覧なら箇所の本文）にそのまま出てくる |
  | `agrees with a computed place` | 同じ事実の、計算した箇所が同じ値 |
  | `agrees with another place read blind` | 同じ事実の別の箇所を、別のセッションの目隠しの読み手が同じ値に読んだ |
  | `read the same by a second model` | 測定済みの、モデルの違う 2 つの読み手が、どちらも目隠しで同じ値に読んだ |

  目隠しの読み手には、その箇所の本文だけを渡し、ファイルを読む手段を与えない。ほかの箇所が見えていた読み手の「一致」は、写しただけかもしれないので数えない。1 回のセッションで読ませるのは、事実ごとに 1 箇所まで。
- **測定済みの読み手**とは、そのモデルの最新の測定（`python -m pw.calibrate`、結果は `pw-calibration.json`）が規則の表の基準を満たすもの。測定は、箇所の本文の値をわざと別の値に書き換えて目隠しで読ませる。書き換えた側が正解を知っているので、人の判定は要らない。基準は 2 つの率の 95% 限界で書く（このリポジトリでは、書き換えた値を読める率が 0.85 以上、元の値に引きずられる率が 0.15 以下）。測定のないモデルや、モデルが記録されていない読みは `blind` に数えない。
- 数が残っているのはここだけで、それは測定の件数から出た限界値と、プロジェクトが決めた基準の比較になっている。規則の表そのものは推定ではなく決定で、変えるときは `pw-rules.json` を書き換える（差分としてレビューに出る）。
- 同じ箇所について読み手の値が割れたら「係争」として止め、人がどちらかを却下する。
- 事実の判定は、箇所どうしが一致し、どの読みも規則のどれかを満たしていれば ok。満たさない読みには、どの条件が欠けているかを `pw.check` が表示する。

### 回し方

```
python -m pw.check       # 変換式の箇所を読み直し、箇所どうしを比べる。エージェントなし
python -m pw.maintain    # 加えて、変わった箇所・未読の箇所を目隠しのエージェントに読ませる。規則を満たさない読みは別のモデルにも読ませる
python -m pw.confirm     # （任意）エージェントの読みを、根拠の一文と並べて人が確認する。係争の裁定もここ
python -m pw.discover    # 宣言に漏れている箇所と、まだ宣言されていない事実をエージェントに探させる
```

### 箇所を探す

`pw.check` が比べるのは `pw-facts.json` に書いた箇所だけで、書かれていない箇所は食い違っても何も言われない。`python -m pw.discover` は、その漏れをエージェントに探させる。

| 探すもの | 内容 |
|----------|------|
| 追加の箇所 | 宣言済みの事実ごとに、それを述べているほかの箇所 |
| 新しい事実 | 2 箇所以上で述べられているのに、まだ宣言されていない事柄 |

- エージェントはファイルを読めるだけで、書き換えも実行もできない。報告は専用の道具（`add_place`、`new_fact`）で行い、1 件ずつファイルと照合してから受け取る。

  | 照合 | 落とすもの |
  |------|-----------|
  | 箇所が実在する（ファイル、見出し、名前、キー） | 存在しない箇所 |
  | 根拠の一文が箇所に一字一句ある | 作文された根拠 |
  | 値が根拠の一文に出てくる（一覧なら箇所の本文に全部ある） | 文面にない値 |
  | 読み方（`find` など）を付けたなら、それで計算した値が報告の値と同じ | 動かない読み方 |

- 照合が見るのは「その値がそこに書いてある」までで、「同じ事柄を述べている」かどうかは見ない。同じ値がたまたま書いてあるだけの箇所も通る。
- 受け取ったものは**提案**で、読みではない。探したエージェントは全部の箇所を同時に見ているので、その値は記録しない。`--apply` で `pw-facts.json` に書き込んだあと、`pw.maintain` が新しい箇所を目隠しで読み、`pw.check` が比べる。
- どの提案を採るかは、`pw-facts.json` の差分を見る者が決める。値が食い違う箇所も提案に含まれる（それが知りたいこと）。
- 宣言済みの箇所を隠して探させる測定では、隠した 16 箇所のうち 15〜16 箇所を見つけ直した。何も与えずに事実そのものを探させると、結果はモデルと回によって大きく変わる（`experiments/discovery/RESULTS.md`）。

### 記録

記録はリポジトリ直下の `pw-log.jsonl`。1 行 1 イベントの JSON で、追記だけする。読みと人の確認はコミットと一緒に残り、別の環境でクローンしても同じ判定になる。ブランチどうしは、両方が足した行を両方残してマージする（`.gitattributes` の `merge=union`。同じ行が重なっても結果は変わらない）。

テキストファイルは誰でも書き換えられるので、やり直せるものは記録を信じない。

| 記録の中身 | 扱い |
|------------|------|
| 変換式による読み | 確認のたびに計算し直す。記録された値は使わない |
| 証明 | 本文を記録してあり、`python -m pw.check --verify` で Lean に通し直す。通らないものがあれば失敗 |
| エージェントの読み | 内容のハッシュ（単一の値なら根拠の一文）に結びつく。内容が変われば無効 |
| 人の確認 | 検証できない。その行を足したコミットがレビューを通ったことが担保 |
| コードとモデルの突き合わせ、テストの結果 | 記録を使う。テストは作業ツリーが変われば再実行する。突き合わせの再実行は未対応 |

作業ツリーの同一性は、追跡されている全ファイルの内容と未コミットの変更で決める。記録ファイル自身は除くので、記録への追記やそのコミットで、以前のテスト結果が無効になることはない。

### CI

`.github/workflows/decisions.yml` が、プッシュとプルリクエストのたびに `python -m pw.check --verify` とテストを走らせる。エージェントは使わない。

| 状況 | CI | 直し方 |
|------|----|--------|
| 箇所どうしが食い違う、決定が破られた | 失敗 | ファイルを直す（どの箇所が正しいかは人が決める） |
| 散文の箇所が変わって読みが失効した | 失敗 | 手元で `python -m pw.maintain` を回し、`pw-log.jsonl` をコミットする |
| エージェントの読みが規則のどれも満たさない（欠けている条件が表示される） | 失敗（`--unconfirmed warn` なら警告） | 手元で `python -m pw.maintain`。読み手が未測定なら `python -m pw.calibrate`。人が確認するなら `python -m pw.confirm` |
| 同じ箇所の読みが読み手の間で割れた | 失敗 | 人が `python -m pw.confirm` でどちらかを却下する |
| 記録にある証明が Lean を通らない | 失敗 | 記録が書き換えられている |

CI が取ってくるものは、付け替えられる名前ではなく中身で固定している。

| 取ってくるもの | 固定の仕方 |
|----------------|------------|
| GitHub のアクション（checkout、setup-python） | コミットのハッシュ。どちらも Node.js 24 で動く版 |
| Python のパッケージ | `requirements-ci.txt` に版とハッシュ。`pip install --require-hashes` |
| Lean | 版と、アーカイブの SHA-256 |

固定した版は、どれも公開から 2 週間以上たっているものを選んだ。ジョブの権限はリポジトリの読み取りだけで、チェックアウト後に認証情報を残さない。キャッシュのアクションは使っていない。

CI が使う Lean の版はワークフローに書いてあり、`lean-toolchain` と同じでなければならない。この重複は「Lean の版」という事実の箇所として宣言してあるので、片方だけ変えると CI 自身がそれを報告する。

このリポジトリ自身の `pw-facts.json` には 14 の事実を、文書 14 箇所・コードと設定 24 箇所で宣言してある。最初の 6 つ（16 箇所）は手で書いた。残りは `pw.discover` が提案したものから採った。実走の記録は `experiments/facts/RESULTS.md` と `experiments/discovery/RESULTS.md`。
