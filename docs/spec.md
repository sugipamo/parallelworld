# 事実と箇所：同じことを述べている箇所を、一致させ続ける

v0.5。プロジェクトは同じ事柄を何箇所にも書く。コードの既定値と文書の記述、2 つの設定ファイルの版、文書が列挙しコードが定義する名前の一覧。片方だけが変わると、誰も気づかないまま食い違う。この仕組みは、そういう事柄（**事実**）と、それを述べている**箇所**を宣言しておき、全部の箇所が同じ値として読めることを確かめ続ける。決めるのはそれだけ。

| 問い | 誰が答えるか |
|------|--------------|
| その箇所は何と言っているか | 宣言された読み方（パターン）による計算。それがない箇所は、その箇所だけを見せたエージェント（目隠しの読み手）か人 |
| 箇所どうしは一致しているか | 読んだ値どうしの等式を Lean が判定する |
| その読みを当てにしてよいか | プロジェクトが書く規則の表（`pw-rules.json`）。確率は計算しない |
| 食い違ったとき、どれが正しいか | 人の指示が書いてあれば、それ（公理として扱う）。なければ決めない。指示どうしが食い違えば、どちらも使わず人に戻す |

**範囲は、宣言したものだけ。** 事実として宣言した事柄については、見落としを指摘する。箇所どうしの食い違い、宣言から漏れている箇所、宣言どおりに読めなくなった箇所。宣言していない事柄には関与しない。宣言されていない重複、振る舞いや書式についての記述、手順の正しさは、この仕組みの対象ではなく、「まだできていないこと」でもない。何を宣言に入れるかは、頼まれたときに探索役が提案し、`pw-facts.json` の差分として入る。

v0.4 までにあった主張・接続・確率の区間・並列ワーカーの層は削除した（§7）。

## 2. 事実と箇所

プロジェクトの「事実」を、リポジトリ直下の `pw-facts.json` に列挙する。事実は一つの事柄（既定値、許可リスト、上限、版、名前の一覧など）で、型のついた値を持つ。それを述べている箇所を全部挙げる。

```json
{"name": "axioms a proof may depend on", "type": "List String",
 "gloss": "the axioms an accepted proof may depend on, sorted alphabetically (capital letters first)",
 "places": ["docs/spec.md::3. Lean Gate",
            {"at": "pw/lean_gate.py::ALLOWED_AXIOMS", "read": {"find_all": "\"([^\"]+)\"", "as": "string", "sort": true}}]}
```

- 型は Lean の型で書く。使ってきたのは `String`、`Nat`、`Int`、`List String`、`List Nat`。
- 説明文（`gloss`）は、その箇所だけを見せられた読み手に渡す問いになる。表記（単位、接頭辞の有無、並び順）と範囲まで決めて書く。
- 箇所は `path` か `path::箇所`。読み方（`read`）を付けた箇所は Kernel が読む。付けない箇所はエージェントか人が読む（`read_place`）。
- 読み方は宣言で書く。式は書けない。

  | キー | 意味 |
  |------|------|
  | `find` | グループを 1 つ持つ正規表現。箇所の中でちょうど 1 回一致しなければならず、グループの中身が値になる |
  | `find_all` | 同じ形で、一致を全部とって一覧にする |
  | `within` | グループを 1 つ持つ正規表現（またはその並び）。ちょうど 1 回一致しなければならず、`find`・`find_all` はそのグループの中だけを探す。同じ形のものが箇所にいくつもあるとき、どれのことかを言う（`--format` の近くの選択肢、ある構造体の中、ある一覧の中） |
  | `rewrite` | `[パターン, 置き換え]`。取り出した各片がパターンに全体として一致しなければならず、置き換えには `\1`〜`\9` だけが使える。その箇所だけ表記が違うとき、ほかの箇所の表記に直す（`py310` を `3.10` に） |
  | `as` | 値の種類：`string`、`nat`、`int`、`permille`（小数を千分率の自然数に。割り切れなければ失敗） |
  | `sort` / `unique` | 一覧を並べ替える（文字列はコードポイント順、数は大きさ順）／重複を除く |

  何も評価しないので、同じ宣言はどの実装でも同じ意味になる。正規表現は主要な処理系に共通する範囲に限る（先読み・後読み、後方参照、名前つきグループは不可。`^` と `$` は行頭・行末）。
- 事実の同一性は名前と型で決まる。箇所の一覧や読み方を変えても同じ事実のままで、それまでの読みと人の確認は引き継がれる。
- 説明文（`gloss`）を変えたときは別。説明文は読み手に渡す問いそのものなので、変える前の読み・断り・人の確認は別の問いへの答えになり、数えない。その事実の、エージェントが読む箇所と、目隠しで確認する箇所は読み直しになる（`pw.check` がそう表示し、`pw.maintain` が読ませる）。
- 決定は「全部の箇所が同じ値として読める」。どの箇所も特別扱いしない。食い違ったとき、どれが正しいかは人が決める。人がすでに決めて指示として書いてあれば、それに照らす（下の「人の指示」）。
- 一覧の事実には、**一部だけを挙げている箇所**も宣言できる（`{"at": ..., "some": true}`。読み方を付けてもよい）。設定例は使えるキーの一部を使い、特徴の一覧は命令の一部を挙げる。そういう箇所は全部を挙げなくてよいが、挙げたものは全体の一覧に入っていなければならない。例に存在しないキーが書いてあれば食い違いになる。
  - 全体を述べている箇所が少なくとも 1 つ要る。全体を述べる箇所どうしは一致、一部を挙げる箇所は包含（`∀ x ∈ 一部, x ∈ 全体`）で、どちらも Lean が判定する。
  - 読み手には別の問いを渡す（「この箇所が挙げているものだけを答える」）。全体として読んだ読みは、一部としての読みに流用されないし、逆も同じ。
- 値を変えるときは、全部の箇所を変える。決定を書き直す必要はない。
- 箇所どうしが一致するかどうかは、読んだ値どうしの等式として Kernel が Lean に通す。成り立つこと、または成り立たないことが証明されたときだけ記録し、どちらも示せなければ「未決」とする。
- エージェントが読むときは、根拠の一文（その箇所にある、それを言っている文や表の行）を付ける。Kernel はそれが箇所に一字一句あることを確かめ、人が確認するときに見せる。単一の値の読みは、根拠の一文が残っているかぎり有効。一覧の読みは箇所全体に依存するので、箇所が変われば読み直す。
### 人の指示（公理）

人が「この値はこうである」と決めたことを、事実に書いておける。

```json
{"name": "default mode", "type": "String", "places": ["..."],
 "instructions": [{"is": "fast", "by": "alice", "said": "keep the default on fast", "on": "2026-03-01"}]}
```

- 指示は**公理**として扱う。ファイルの中身から指示が誤りだと示すことはできず、箇所のほうを指示に照らす。`by`（誰の指示か）は必須。`said`（元の言葉）と `on`（いつ）は任意。値は JSON で書く。
- **指示があるとき**は、箇所どうしを比べる代わりに、各箇所を指示と比べる。違っている箇所は「誰の指示に反しているか」つきで報告する。指示がないときは「食い違っている」としか言えなかったものが、どの箇所が直すべき側かまで言える。
- **指示どうしが食い違うとき**（Lean が「等しくない」を示したとき）は、関わった指示を全部わきに置く。先に出された指示も後の指示も、多くの人が同じことを言っている側も、同じに扱う。矛盾した公理からは何でも導けてしまうので、どちらからも何も結論しない。その事実は指示なしとして箇所どうしの一致だけを見て、状態を「衝突」とし、人が片方を取り下げるのを待つ。**ほかの事実には影響しない。**
- どちらの指示が有効かは、Kernel は決めない。数学が両立しない公理を前にしたときと同じで、選ぶのは人。「新しい指示が勝つ」のような自動の規則は置いていない。
- 指示を書き込むのは人か、人の指示を受けたエージェント。探索役は指示を足しも変えもしない。

```
FAIL conflict   fact: default mode
   people's instructions about this cannot both hold (verified by Lean). They are set aside until one is withdrawn:
      alice (2026-03-01): "fast"  "keep the default on fast"
      bob (2026-09-12): "safe"
   judged without them, the fact is: violated
ok   current    fact: limit
```

### 定義

事実は、ほかの事実から式で導く形でも宣言できる。

```json
{"name": "number of conditions a rule may ask for", "type": "Nat",
 "defined": {"from": ["conditions a rule may ask for"], "as": "fun cs => cs.length"},
 "places": [{"at": "docs/spec.md::読みが成り立つ条件", "read": {"find": "規則に使える条件は次の (\\d+) つ", "as": "nat"}}]}
```

- `from` に挙げた事実の値を、`as` の Lean の関数に渡したものが、この事実の値になる。型が合うかは宣言の時点で Lean が確かめる。
- **定義は新しい主張を足さない。** 値は元の事実から決まるので、定義が原因で矛盾することはない。その代わり、定義された事実には指示を書けない。値を定めたいなら、元の事実に指示を書く。
- 各箇所は、定義が与える値と比べる。違っていれば「定義が与える値と違う」と報告し、その値（Lean に計算させたもの）を表示する。直すのは箇所か、元の事実のどれか。
- **元の事実が決まっていないあいだは「待ち」になる。** 元の事実の箇所どうしが食い違っている、読めていない、指示が衝突している、のどれでも、比べる相手がないので何も判定しない。元の事実に人の指示があれば、箇所がそれに追いついていなくても、定義は指示の値に従う。
- 定義を定義から作ることもできる。自分自身に戻る定義は宣言の時点で拒否する。
- 個数、先頭や末尾の要素、最小・最大、差分のように、Lean の標準の関数で書けるものを想定している。「同じ値」「一覧に含まれる」では言えなかった関係を、これで言う。

### 書き戻しと仮説

`pw.check` は箇所を読んで指示と比べる。`python -m pw.propagate` はその逆で、指示の値を、それと違っている箇所に書き込む。

- **機械的に書けるのは、単純なパターン（`find` で 1 つの値を取るもの。`within` は可、`rewrite` は不可）で読む箇所だけ。** パターンのグループが一致した部分を新しい値で置き換え、ほかには触れない。
- **書いたものは読み戻して確かめる。** 同じパターンで読んで、指示の値が返らなければ書かない。書く側を信じず、読んで確かめる点はチェックと同じ。
- 一覧、表記を書き換えている箇所、エージェントが読む散文、JSON の中のキーは、パターンを逆にしても書き方が決まらない。既定では「手で直す箇所」として挙げる。
- **`--agent` を付けると、そういう箇所の新しい本文をエージェントに出させる。** エージェントには箇所の本文と値だけを見せ、ファイルには触らせない。答えは道具経由で受け取り、次の 3 つを満たしたものだけを当てはめる。

  | 検査 | 落とすもの |
  |------|-----------|
  | 変更が小さい | 値を変える代わりに書き直してしまった本文 |
  | 同じファイルの、ほかの宣言済みの箇所の読みが変わらない | 巻き添えで別の事実を変えてしまう編集 |
  | 読み戻すと定めた値になる。パターンで読む箇所はパターンで、散文は、新しい本文だけを見せた目隠しの読み手（何と読めるはずかは知らせない）で | 値が入っていない、別の値に読める本文 |

  エージェントは「ほかの記述を変えずには直せない」と断ることもできる。その箇所は手で直す側に残る。宣言されていない部分への影響は検査できないので、差分を見て確かめる。
- 書き手のエージェントには、同じ事実をパターンで読んでいる箇所（たいていはコード）の本文を参考として一緒に見せる。新しい項目を足すとき、その説明（引数、一文の説明）をそこから取らせ、参考にないことは書かせないため。書き手は目隠しではない。確かめるのは別の、目隠しの読み手。
- 既定では差分を表示するだけで、`--apply` を付けたときにファイルを書き換える。
- **仮説**: `--suppose '事実の名前=値'` は、誰も定めていない値を仮に置く。置いた値は、指示がもう 1 つ増えたものとして扱う。既にある指示と食い違うことを Lean が示せば、そう報告して、その事実には何も書かない。食い違わなければ、どの箇所をどう書き換えることになるかを示す。仮に置いただけでは宣言は変わらない。指示にするのは人。

数学の言葉との対応は次のとおり。

| 数学 | この仕組み |
|------|-----------|
| 値 | 箇所の読み |
| 公理 | 人の指示。箇所はこれに照らす。衝突したものはわきに置く |
| 仮説 | `--suppose` で仮に置いた値。帰結（衝突するか、どこを書き換えるか）を見るだけで、採用はしない |
| 定理 | 「箇所が一致する」「指示と同じである」という Lean の判定 |
| 予想 | まだ規則を満たしていない読み（`--unconfirmed warn` で警告として扱える） |
| 定義 | ほかの事実から式で導く事実。新しい主張を足さないので、衝突しない |

### 読みが成り立つ条件

- 読みが成り立つかどうかは、確率ではなく**規則の表**で決める（`pw-rules.json`。置かなければ `pw/rules.json` の既定）。表は「次の条件がそろえば成り立つ」という行の並びで、どれか 1 行を満たせばよい。

  | このリポジトリの規則 | 意味 |
  |------|------|
  | `computed` ＋ `read the same blind` | 宣言された読み方で計算した読みで、その箇所だけを見た目隠しの読み手も同じ値を読み取った |
  | `confirmed by a person` | 人が文面と見比べた |
  | `blind` ＋ `words occur in the place` ＋ `agrees with a computed place` | 目隠しの読み手が読み、値が文面にそのままあり、計算した箇所と同じ値 |
  | `blind` ＋ `words occur in the place` ＋ `contained in a computed place` | 一部を挙げる箇所について：目隠しの読み手が読み、値が文面にそのままあり、挙げたものがすべて計算した箇所の一覧に入っている |
  | `blind` ＋ `words occur in the place` ＋ `read the same by a second model` | 計算した箇所との照合の代わりに、別のモデルも目隠しで同じ値を読んだ |

  規則に使える条件は次の 9 つで、どれも Kernel が記録とファイルから判定する。

  | 条件 | 中身 |
  |------|------|
  | `computed` | その箇所に読み方（`pattern`、`reader`）が宣言されている |
  | `confirmed by a person` | 人の確認が記録にある |
  | `blind` | 測定済みの読み手が、その箇所の本文だけを渡されて読んだ |
  | `words occur in the place` | 読んだ値が、根拠の一文（一覧なら箇所の本文）にそのまま出てくる |
  | `agrees with a computed place` | 同じ事実の、計算した箇所が同じ値 |
  | `agrees with another place read blind` | 同じ事実の別の箇所を、別のセッションの目隠しの読み手が同じ値に読んだ |
  | `read the same by a second model` | 測定済みの、モデルの違う 2 つの読み手が、どちらも目隠しで同じ値に読んだ |
  | `read the same blind` | 計算する箇所について：測定済みの読み手が、その箇所の本文だけを渡されて、読み方が計算するのと同じ値を読み取った |
  | `contained in a computed place` | 一部を挙げる箇所について：挙げたものがすべて、同じ事実の計算した箇所（全体を述べるもの）の一覧に入っている |

  目隠しの読み手には、その箇所の本文だけを渡し、ファイルを読む手段を与えない。ほかの箇所が見えていた読み手の「一致」は、写しただけかもしれないので数えない。1 回のセッションで読ませるのは、事実ごとに 1 箇所まで。
- 読み方（`find` など）は値を計算するが、その値が問われている事柄のものかどうかは示さない。たまたま同じ数字が書いてあるだけの箇所にも、読み方は書ける。そこで計算する箇所も、目隠しの読み手に一度見せる。読み手が同じ値を読み取れば成り立ち、その確認は読み方が変わらないかぎり有効（箇所の中身が変わっても読み直さない）。
- 箇所が小さくて（JSON のキー 1 つ、1 行の定義など）それだけでは何の値か分からないときは、ファイルの中でそれを囲んでいる部分も一緒に見せる（JSON なら親のオブジェクト、ほかは前後の数行）。値は箇所そのものから読ませる。同じ事実の別の箇所が同じファイルにあるときは見せない。
- 目隠しの読み手の答えは 2 通りで、値を読む（`read_place`）か、その箇所は問われた事柄を述べていないと断る（`not_stated`、理由つき）。どちらもしなかった箇所は「無回答」で、箇所についての結果ではなくセッションの失敗として報告する。
- **測定済みの読み手**とは、モデルと、読み手に渡す指示文（`pw/reader.txt`）の組で、いまの指示文のもとで行った測定（`python -m pw.calibrate`、結果は `pw-calibration.json`）を**全部足し合わせた件数**が規則の表の基準を満たすもの。最新の 1 回だけを見ないのは、通るまで測り直しても意味がないようにするため。指示文を変えたら、それまでの測定はその読み手のものではなくなり、測り直しになる。測定は、正解がこちらに分かっている 2 種類の課題でできている。一つは、箇所の本文の値をわざと別の値に書き換えて読ませる（書き換えた値を読めるか、元の値に引きずられないか）。もう一つはおとりで、ある事実の箇所を、同じ型の別の事実の問いと一緒に見せる（断るのが正解で、値を読んでしまえば誤り）。基準は 3 つの率の 95% 限界で書く（このリポジトリでは、書き換えた値を読める率が 0.85 以上、元の値に引きずられる率が 0.15 以下、おとりを読んでしまう率が 0.15 以下）。無回答の試行はどの率にも入れない。測定のないモデル、基準にある率を測っていないモデル、モデルが記録されていない読みは数えない。
- 数が残っているのはここだけで、それは測定の件数から出た限界値と、プロジェクトが決めた基準の比較になっている。規則の表そのものは推定ではなく決定で、変えるときは `pw-rules.json` を書き換える（差分としてレビューに出る）。
- 同じ箇所について読み手の値が割れたら「係争」として止め、人がどちらかを却下する。
- 事実の判定は、箇所どうしが一致し、どの読みも規則のどれかを満たしていれば ok。満たさない読みには、どの条件が欠けているかを `pw.check` が表示する。

### 回し方

```
python -m pw.check       # パターンで読む箇所を計算し直し、箇所どうしを比べる。エージェントなし。記録には書かない（--record で書く）
python -m pw.maintain    # 加えて、変わった箇所・未読の箇所を目隠しのエージェントに読ませる。規則を満たさない読みは別のモデルにも読ませる
python -m pw.confirm     # （任意）エージェントの読みを、根拠の一文と並べて人が確認する。係争の裁定もここ
python -m pw.discover    # 宣言したものの面倒を見る：読めなくなった箇所の付け替えと、漏れている箇所の探索。--new で新しい事実の提案も
python -m pw.propagate   # 人が定めた値を、それと違う箇所に書き戻す（差分の表示。--apply で適用）。--suppose で仮の値を試す。--agent で一覧や散文も
```

### 箇所を探す

`python -m pw.discover` は、宣言した事実の面倒を探索役（エージェント）に見させる。宣言の中身（どこに書いてあるか、どう読むか）を手で保守する代わりに、探索役が提案し、目隠しの読み手が確かめる。

| すること | 内容 | いつ |
|----------|------|------|
| 付け替え | 宣言どおりに読めなくなった箇所（ファイルや見出しや名前が変わった、パターンが合わなくなった）について、その記述がいまどこにあるかを探し、箇所と読み方を出し直す | 既定 |
| 追加の箇所 | 宣言済みの事実ごとに、それを述べているのに宣言から漏れている箇所を探す | 既定 |
| 新しい事実 | 2 箇所以上で述べられているのに、まだ宣言されていない事柄を提案する | `--new` を付けたときだけ |

- 宣言していない事柄は、既定では探さない。範囲に入れるのは別の一歩で、頼んだときだけ行う。
- 宣言した箇所が見つからないとき、Kernel は黙って別のもの（ファイル全体など）を読まず、「宣言どおりに読めない」と報告する。付け替えはその報告から始まる。
- 探索役は、その記述がもうどこにもないと判断したら、そう報告できる（`gone`）。ただし、宣言から箇所を外すのは人がする。探索役の提案で宣言が減ることはない。

- エージェントはファイルを読めるだけで、書き換えも実行もできない。報告は専用の道具（`replace_place`、`add_place`、`new_fact` など）で行い、1 件ずつファイルと照合してから受け取る。

  | 照合 | 落とすもの |
  |------|-----------|
  | 箇所が実在する（ファイル、見出し、名前、キー） | 存在しない箇所 |
  | 根拠の一文が箇所に一字一句ある | 作文された根拠 |
  | 値が根拠の一文に出てくる（一覧なら箇所の本文に全部ある） | 文面にない値 |
  | 読み方（`find` など）を付けたなら、それで計算した値が報告の値と同じ | 動かない読み方 |

- 照合が見るのは「その値がそこに書いてある」までで、「同じ事柄を述べている」かどうかは見ない。同じ値がたまたま書いてあるだけの箇所も通る。探したエージェント自身に聞いても当てにならない。ほかの箇所を全部見ているので、同じ数字は同じ事柄に見える。
- そこで、照合を通った提案は 1 箇所ずつ、**その箇所だけを見せた目隠しの読み手**に、事実の説明文と一緒に渡す。

  | 読み手の答え | 扱い |
  |--------------|------|
  | 値を読み取った（読み方つきの箇所なら、読み方が計算する値と同じ） | 採る。ほかの箇所と値が違っていても採る（それが知りたい食い違い） |
  | 値を読み取ったが、読み方が計算する値と違う | 落とす。読み方がその箇所の言っていることを読んでいない |
  | この箇所はその事柄を述べていない、と断った | 落とす。読み手の理由を表示する |
  | どちらもしなかった | 未確認。書き込まず、失敗として報告する |

- 探索の失敗が「何も見つからなかった」に見えないようにしてある。
  - 探索役は、事実ごとに「探し終えた」と道具で申告する。申告のない事実、報告の道具が起動しなかったセッション、エラーで終わったセッションは「未完了」と表示し、終了コードを 1 にする。
  - 宣言済みの事実ごとに、既知の箇所を 1 つ探索役に伏せておく（対照）。探索がそれを挙げてこなければ、その事実の探索は疑わしいと表示する。
- `--apply` を付けると、採った箇所を `pw-facts.json` に書き込む。目隠しの読みは記録に残るので、続けて `pw.maintain` を回せば読み直しは要らない。付けなければ記録の写しの上で動き、表示するだけ。
- 目隠しの読み手で落とせない種類もある。ある回の実験の記録のように、その箇所だけ読めば現在の事実を述べているように見える文は通る。最後に `pw-facts.json` の差分を見る者の判断は残る。
- 宣言済みの箇所を隠して探させる測定では、隠した 16 箇所のうち 15〜16 箇所を見つけ直した。何も与えずに事実そのものを探させると、結果はモデルと回によって大きく変わる。手で判定した 7 件の提案を目隠しの読み手に見せると、6〜7 件で手の判定と一致した（`experiments/discovery/RESULTS.md`）。

### 記録

記録はリポジトリ直下の `pw-log.jsonl`。1 行 1 イベントの JSON で、追記だけする。読みと人の確認はコミットと一緒に残り、別の環境でクローンしても同じ判定になる。ブランチどうしは、両方が足した行を両方残してマージする（`.gitattributes` の `merge=union`。同じ行が重なっても結果は変わらない）。

**確かめるだけなら、記録は増えない。** `pw.check` は記録の写しの上で動き、プロジェクトの記録には書かない。試しにファイルを書き換えて確かめても、採用しなかった状態の読みが記録に残ることはなく、手元と CI で記録の中身がずれることもない。`pw.check` が求めるもの（パターンによる読み、箇所どうしの等式とその証明）は、次に確かめるときにまた求め直すので、書かなくても何も失われない。記録に書くのは次のとき。

| 書くもの | 書く内容 |
|----------|----------|
| `pw.maintain` | 目隠しの読み手の読みと断り。あわせて、そのとき確かめた結果（計算した読み、等式、証明） |
| `pw.confirm` | 人の確認と却下 |
| `pw.discover --apply`、`pw.propagate --apply` | 採った箇所・書き戻した本文についての読み |
| `pw.check --record` | 確かめた結果だけ。頼んだときに限る |

増えた行は、それを生んだ変更と一緒にコミットする。

テキストファイルは誰でも書き換えられるので、やり直せるものは記録を信じない。

| 記録の中身 | 扱い |
|------------|------|
| 読み方（パターン）による読み | 確認のたびに計算し直す。記録された値は使わない |
| 証明 | 本文を記録してあり、`python -m pw.check --verify` で Lean に通し直す。通らないものがあれば失敗 |
| エージェントの読み | 内容のハッシュ（単一の値なら根拠の一文）に結びつく。内容が変われば無効 |
| 人の確認 | 検証できない。その行を足したコミットがレビューを通ったことが担保 |

## 3. Lean Gate

箇所どうしの一致は、読んだ値を Lean の項として並べた等式（`(a : T) = (b : T) ∧ …`）で述べ、Kernel が決まったタクティク（`rfl`、`decide`、`simp`）で「成り立つ」か「成り立たない」かを示そうとする。

- 定理の文面は Gate が書く。値は読み手やパターンから来た文字列なので、文面に差し込む前にふるいにかける（新しい命令を始められる語や記号を含むものは拒否。拒否リスト方式で、弱点であることは分かっている）。型に合わない値は、述べられた時点で拒否する。
- 検証は Lean を 2 回走らせる。1 回目で文面とタクティクを含むモジュールをコンパイルし、2 回目は外から来た文字列を一切含まないファイルからそれを import して `#print axioms` する。
- 受理条件：1回目が成功し、2回目の出力が公理レポート1行だけで、許可リスト（`propext`、`Classical.choice`、`Quot.sound`）に収まる。
- 2 回に分ける理由：タクティクは任意のメッセージを出力できる。1 ファイルで済ませていた初版は、`trace` で偽の公理レポートを出すと `1 = 2` の「証明」を受理した。
- Gate は実行中の Lean の版が `lean-toolchain` と一致しなければ何も受理しない。証明のイベントには、版・`lean/Gamma.lean`・許可リストから作ったハッシュを記録する。
- 記録に「成り立つ」と「成り立たない」の両方の証明があるときは、どちらかを選ばずに「争いあり」と表示する。`python -m pw.check --verify` が、Lean を通らないほうを特定する。

## 4. 読み手の道具（MCP）

読み手のセッションに与える道具はこの 2 つだけで、ファイルを読む手段もほかの操作もない。

| ツール | 内容 |
|--------|------|
| `read_place(h, place, object, quote)` | 事実の箇所の一つが何と言っているかを、根拠の一文つきで述べる。比較は Kernel がする |
| `not_stated(h, place, why)` | 見せられた箇所がその事実を述べていないと答える（別の事柄を述べている、値を言っていない）。黙っているのとは区別して記録する |

## 5. CI

`.github/workflows/decisions.yml` が、プッシュとプルリクエストのたびに `python -m pw.check --verify` とテストを走らせる。エージェントは使わない。記録は読むだけで、CI が記録を増やすことはない。

| 状況 | CI | 直し方 |
|------|----|--------|
| 箇所が人の指示と違う | 失敗。どの箇所が誰の指示に反しているかが表示される | 箇所を直す。指示のほうが古くなっているなら、指示を出した人に取り下げてもらう |
| 人の指示どうしが食い違う | 失敗（その事実だけ）。指示はわきに置かれる | 指示を出した人どうしで決め、片方を `pw-facts.json` から外す |
| 箇所どうしが食い違う。一部を挙げる箇所に、全体にないものがある | 失敗 | ファイルを直す（どの箇所が正しいかは人が決める） |
| 宣言した箇所が宣言どおりに読めない（ファイル・見出し・名前がなくなった、パターンが合わない） | 失敗 | `python -m pw.discover --apply` で探索役に付け替えさせ、コミットする |
| 散文の箇所が変わって読みが失効した | 失敗 | 手元で `python -m pw.maintain` を回し、`pw-log.jsonl` をコミットする |
| 読みが規則のどれも満たさない（欠けている条件が表示される）。読み方つきの箇所を目隠しの読み手がまだ見ていない場合を含む | 失敗（`--unconfirmed warn` なら警告） | 手元で `python -m pw.maintain`。読み手が未測定なら `python -m pw.calibrate`。人が確認するなら `python -m pw.confirm` |
| 目隠しの読み手が「この箇所はその事柄を述べていない」と断った | 失敗。理由が表示される | 別の事柄なら、その箇所を `pw-facts.json` から外す |
| 同じ箇所の読みが読み手の間で割れた | 失敗 | 人が `python -m pw.confirm` でどちらかを却下する |
| 記録にある証明が Lean を通らない | 失敗 | 記録が書き換えられている |

CI が取ってくるものは、付け替えられる名前ではなく中身で固定している。

| 取ってくるもの | 固定の仕方 |
|----------------|------------|
| GitHub のアクション（checkout、setup-python） | コミットのハッシュ。どちらも Node.js 24 で動く版 |
| Python のパッケージ | `requirements-ci.txt`（動かすのに要るもの）と `requirements-test.txt`（このリポジトリのテスト用）に版とハッシュ。`pip install --require-hashes` |
| Lean | 版は `lean/lean-toolchain`、アーカイブの SHA-256 は `ci/lean.sh` |

固定した版は、どれも公開から 2 週間以上たっているものを選んだ。ジョブの権限はリポジトリの読み取りだけで、チェックアウト後に認証情報を残さない。キャッシュのアクションは使っていない。

CI が使う Lean の版は、`lean/lean-toolchain` から読む（`ci/lean.sh`）。以前はワークフローにも版を書いていて、その重複を「Lean の版」という事実の箇所として宣言していた。いまは書く場所が 1 つなので、宣言からは外した。版を上げたのにチェックサムを直し忘れると、`ci/lean.sh` がアーカイブを拒否する。

### ほかのリポジトリの CI

このリポジトリはアクションとして使える（`action.yml`）。ほかのリポジトリのワークフローは `uses: sugipamo/parallelworld@<コミット>` の 1 ステップで、上と同じ手順（Python、パッケージ、Lean、`pw.check --verify`）を、そのリポジトリの `pw-facts.json` に対して走らせる。このリポジトリ自身のワークフローも同じアクションを使っている（`uses: ./`）。

- 使う側が固定するのは、このリポジトリのコミット 1 つ。パッケージのハッシュ、Lean の版とチェックサムは、そのコミットの中で決まる。使う側に写す値がないので、版を上げたときに直し忘れる場所もない。
- 使う側に入るのは、動かすのに要るパッケージだけ（`requirements-ci.txt`）。
- Lean は、アクションを置いた場所ではなく、利用者のキャッシュ（`PW_LEAN_WORK`、なければ `~/.cache/parallelworld`）に写したプロジェクトの上で動かす。仕組みを置いた場所は読むだけでよい。

このリポジトリ自身の `pw-facts.json` には 9 つの事実を、文書 3 箇所・コードと設定 16 箇所で宣言してある（許可される公理、読み手の道具の名前、Lean の版、規則に使える条件とその個数、読み手の基準 3 つ、読み手の既定のモデル）。うち 2 箇所は一部を挙げる箇所で、規則の表が使っている条件名が、Kernel の知っている条件に含まれることを確かめている。条件の個数は定義で、条件の一覧から導いている。

## 6. 範囲の外と、限界

### 範囲の外（関与しない）

次のものは対象にしない。調べもしないし、何も言わない。

- **宣言されていない事柄。** 同じことが何箇所に書いてあっても、宣言されるまでは見ない。
- **振る舞い・書式・手順についての記述。** 「この例は有効な入力である」「既存の値が優先される」のような文が実際にそうなっているかは、対象のコードを動かさないと分からない。それはプロジェクト自身のテストの仕事とする。3 つのリポジトリを見たかぎり、README の半分ほどはこの種類だった（`experiments/survey/RESULTS.md`）。
- **式で書けない関係。** 個数や最小値のように、ほかの事実から Lean の関数で導けるものは定義として宣言できる。そう書けない関係（「だいたい同じ」「〜と整合する」）は対象にしない。

### 限界（宣言したものについて）

- **指示は検証できない。** 公理なので、誤って書き込まれた指示も正しい指示と同じ重さを持つ。`by` に書かれた人が本当にそう言ったかは、`pw-facts.json` の差分を見る者しか確かめられない。
- **公理にできるのは、値として書ける指示だけ。** 「この値はこれ」は書ける。「〜に気をつける」「〜の場合は〜する」は書けず、そういう指示どうしの衝突も見えない。見つかる衝突は、同じ事実について違う値を言っている場合だけ。
- **事実をまたぐ衝突は見ていない。** 指示の衝突は 1 つの事実の中でしか調べない。定義された事実には指示を書けないようにしてあるので、「元の事実への指示」と「導かれた値への指示」が食い違う、という形の衝突は起こせないが、見つけてもいない。
- **書き戻せるのは値だけ。** 単純なパターンの箇所は機械的に、一覧や散文はエージェントの提案を読み戻して確かめたうえで書く。エージェントの編集が、宣言されていない記述を変えていないかは検査できない。振る舞いを満たすコードを作ることはしない（範囲の外）。
- **探索役の責任が大きい。** どこを箇所とし、どう読むかは探索役が出す。目隠しの読み手が 1 箇所ずつ確かめるが、探索役が見つけなかった箇所は誰も知らない。伏せた既知の箇所を見つけ直せるかは毎回確かめているが、それは既知の箇所についての話。
- **最初に食い違いを見つける力は、人が一度読むのと変わらない。** 値打ちがあるとすれば、宣言したあとに一致を保ち続けるところ。このリポジトリのほかに、別のリポジトリ 1 つ（miclow）の CI で回し始めたところで、長く使った結果はまだない。
- **読み手も探索役も、同じ系統のモデル。** 同じ読み違いを揃ってする可能性は、測定では消えない。測定の書き換えやおとりは、こちらが作った易しいもの。
- **同じ事柄かどうかは、目隠しの読み手に移しただけ。** 箇所の外の事情（過去の記録である、別プロジェクトのものである）で決まるものは通ることがある。
- **部分を名指しできるのは Markdown・JSON・Python だけ。** ほかの言語はファイル全体が 1 箇所になる。`within` で範囲を絞れるようにはなったが、名指しではない。
- **パターンは、構文ではなく文字の並びを見ている。** 名前の出どころが 2 通りあるもの（デコレータの引数か、なければ関数名）や、属性で名前が変わる構造体のフィールドは、読めるが、最短一致や並びに頼った壊れやすいパターンになる。コードの書き方が変わると黙って別の値を読み、それがほかの箇所とたまたま合っていれば気づかない。正規表現の文字クラスの中身のように、読めないものもある（その場合はエージェントに読ませることになり、箇所が変わるたびに読み直しになる）。構文を見る読み方は足していない。足す場所は 1 か所にしてある（`pw/kernel.py` の `READERS`）。
- **1 つの事実の中で、同じ箇所を 2 通りに読むことはできない。** 同じファイルの中の 2 つの記述を両方挙げたいときは、箇所の名前で分けられる必要がある。
- **新しいリポジトリは、読み手を測るまで何も成り立たない。** 測定の材料は読まれた散文の箇所から作るので、小さいリポジトリでは基準を満たせる件数が作れない。このリポジトリ自身も、層を削ったあとは散文の箇所が 3 つになり、1 回の測定で作れる書き換えは 10 件ほど。いまの読み手の測定は削る前に行ったもので、指示文を変えれば、基準に届くまで何回も測り直すことになる。
- **読みには指示文の識別子を残していない。** モデルが同じなら、前の指示文のもとで読んだものも数えている。
- **途中のコミットではチェックが落ちる。** 読ませる対象はコミット済みの内容なので、宣言や文書を変えたコミットと、読みを記録したコミットが分かれる。
- **Gate のふるいは拒否リスト。** 外から来る文字列は値だけになったが、方式は変わっていない。

## 7. 経緯

v0.4 までは、もっと広い仕組みだった。自然言語の主張（H）を Lean の命題（F）に、接続の仮説（G、M）を介して結び、テストやレビューを証拠として確率の区間を計算し、その下界で並列ワーカーのマージ可否を決める、というもの。事実と箇所は、その中で「過去の決定との矛盾を確かめる」ために後から足した部分だった。

削除した理由は、使われていなかったこと。このリポジトリの運用も、別のリポジトリでの試行（`experiments/external/RESULTS.md`）も、事実と箇所・規則の表・目隠しの読み手・Lean の等式判定だけで回っていた。残っていた層には、根拠のない仮置きの数値（基準率、尤度、閾値）があり、Kernel の半分以上を占めていた。

| 削除したもの | 中身 |
|--------------|------|
| 主張と接続（`claim`、`ground`、`ground_at`、`claim_formal`、`model`） | 自然言語や述語で書いた主張を Lean の命題に結ぶ仮説 |
| 証拠と推論（`observe`、`infer`、`distance`、`pw/credal.py`、`pw/formula.py`、`pw/catalog.json`） | カタログの尤度、クレーダル集合、コピュラ、区間の計算 |
