# 自然言語の決定はどこまで乗るか ― 知見の記録

自然言語で書かれた決定を Kernel に入れたとき、何が起き、何が失われるかを、実際に走らせた結果から書く。
新しい観測が出たら §6 の表に足していく。生のデータは `experiments/nl/results/` にある。

## 1. 調べ方

このプロジェクトの実際の決定を 12 個選んだ（`docs/spec.md`、`docs/symbols.md` から）。うち 1 個はコードに反する偽の決定（N9）、2 個は互いに引っ張り合う決定（N7、N8）。

互いに見えない 3 体のワーカー（claude-opus-5-5）に、各決定を次のどれかに分類させ、実際に Kernel へ入れさせた。

- **Lean**: コードや概念の数学的なモデルについての Lean 命題として書ける。
- **検査**: Lean では書けないが、コマンドでコードに当てられる。
- **なし**: 文にない内容を発明しないかぎり、どちらも無理。

あわせて「文が言っているのに形式化が捉えていないこと（落としたもの）」と「文が決めていないのに形式化が決めたこと（足したもの）」を書かせた。そのあと 4 体目に、3 体の Lean の形式化どうしの関係を Lean で判定させた。

| | 手数 | 費用（表示上） | 所要 |
|---|---|---|---|
| 形式化（1 体あたり、12 決定） | 37〜44 | $0.92〜1.25 | 3.5〜5 分 |
| 判定 | 25 | $0.38 | 3 分 |

各 1 回の実行で、3 体は同じモデル。

## 3. 知見

### 3.1 どの決定がどこまで乗るかは安定している

分類は 12 個すべてで 3 体が一致した。Lean に届いたのは 3 個、検査が 6 個、どちらも無理が 3 個。**実際の決定のうち Lean に乗るのは 4 分の 1、半分は検査どまり**だった。数学的な中身を持つ決定を意図的に 3 個入れての数字なので、ふつうのプロジェクトではもっと低いはず。

### 3.2 形式化が一致しても、文に忠実とは限らない

N1 の文は「確率たち」と言っており、コードも任意個を扱う。3 体は全員、これを 2 個の確率についての命題に縮めた。3 つの形式化は Lean 上で同値で、Kernel はこれを仕様の仮説への支持として数える。しかし一致していたのは**同じ弱め方**だった。

同じモデルの著者どうしは誤りが相関する、という懸念は仕様に書いてあったが、これはその実例。同じモデルによる独立な形式化の一致は、忠実さの証拠としてほとんど使えない。カタログの `independent_formalization`（一致の尤度 0.85 対 0.5）は楽観的すぎる。

### 3.3 コードについての決定が、概念についての定理にすり替わる

N1〜N3 で、3 体は全員 `ground`（閉じた命題）を選び、`ground_at`（コードのモデルに述語を当てる）は誰も選ばなかった。結果は「実数についての不等式」「ベイズの式の恒等式」で、ワーカー自身が「`pw/credal.py` には結びついていない」と書いている。

決定は「このコードはこう振る舞う」だったのに、形式化は「数学としてこれは正しい」になった。証明が通ると主張の確率は上がるが、コードについては何も確かめられていない。**これが今回いちばん大きな損失**で、仕様の仮説の基準率 0.6 という一つの数字の中に埋もれて見えなくなる。

### 3.4 定理になった形式化は、互いに比べられない

閉じた命題は証明された時点ですべて ⊤ に等しくなる。N2 で f3 は他の 2 体と違うモデル（一定の一致率 qⁿ）を使い、N3 で f1 は他の 2 体と全く違う読み（関数の不一致が全称を反証する）を書いたが、Lean はこれらを区別できなかった。

最初の実走で `clamp` と `bound` に起きたのと同じ現象で、あのときは述語と対象に分けて解決した。自然言語から出発すると、ワーカーは分けない形を選ぶ。

### 3.5 中身のない形式化も、証明つきで通る

N3 の f2 と f3 の命題は `π * 0 / (π * 0 + (1 - π) * r) = 0`。分子が 0 なので算術として真で、分母が 0 の場合まで（Lean の 0 除算の規約で）成り立つ。「不一致が反証する」ことについて何も言っていない。それでも証明は受理され、主張の確率は上がる。

述語と対象に分けた形なら「述語を満たさない対象がある」ことを確かめる空虚性の検査が使えるが、閉じた命題には使えない。

### 3.6 「落としたもの」「足したもの」の自己申告は役に立つ

3 体の申告は具体的で、ほぼ正確だった。

- N1: 「2 個だけ。文は個数を言っていない」「コードの表には結びついていない」
- N4: 「証拠の同一性は出自の文字列で決まり、それはエージェントが選ぶ。別の文字列で報告されたら 2 回数えられ、この検査では分からない」
- N5: 「MCP の入口しか見ていない。`ground` は Python からは事前確率を受け取れるし、無作為な検査の範囲 0〜15 はカタログの外に直書きされている」

ただし均一ではない。N1 について f3 は「数学的な内容で落としたものはない」と書き、2 個に固定したことは「足したもの」の側に書いた。同じ事実が、著者によって損失にも補足にもなる。

この申告は数値を動かさないが、接続を人が見るときに必要な情報そのものなので、`ground` / `ground_at` に `left_out` と `added` として保存できるようにした。

### 3.7 検査は、決定の一つの読みを一つの場面で確かめるだけ

検査にされた 6 個で、3 体はそれぞれ違うものを書いた。N9 なら f1 と f3 は `grep`、f2 は自作のスクリプト。N4 なら f1 は 2 つの Kernel を立てる試験、f3 は既存の pytest。同じ文に対する 3 つの代理で、これらの関係を確かめる手段はない（Lean の命題と違って、コマンドには同値を言う代数がない）。

各検査が見ているのは一場面か、構文上の手がかり。ワーカー自身が「`os.system` や、エージェントのタクティクを走らせる Lean そのものは検出しない」（N9）と書いている。

Kernel の側でこの弱さを表しているのは、テストの尤度（通過 0.95 対 0.40）だけ。強い検査も弱い検査も同じ数字になる。

### 3.8 決定が成り立つかどうかが、読みで割れる

N7「独立は決して仮定しない」で、3 体の判定は割れた。

- f1: 偽。同じ主張の G への証拠と H への証拠が、宣言なしに積で結合されている（点 0.857 が返る）。検査は**失敗**。
- f2: 文字どおりには偽。ただし書いた検査は「同じ対象への未宣言の証拠は積にしない」という狭い読みを確かめるもので、**通過**。
- f3: 既定の設定では真。検査は**通過**。ただし `dependence="independent"` という設定が存在することは指摘。

「仮定する」が宣言つきを含むのか、「証拠の間」が同じ対象に限るのか、で結論が変わる。同じ決定が、誰が検査を書いたかで「破られている」にも「守られている」にもなる。

なお f1 の読みは、この実装についての実際の発見でもある。v0.1 の原則は「根拠のない独立性を導入しない」だったが、実装は別々の原子への証拠を条件つき独立として掛け合わせている（`docs/symbols.md` §9 の仮定 3 として書いてはある）。

### 3.9 コードに反する決定は見つかる。決定どうしの矛盾は見つからない

- **決定とコード**: 偽の決定 N9 は、3 体とも検査の失敗として検出した。`pw.check` に入れれば以後も機械的に失敗し続ける。
- **決定と決定**: N7 と N8 の緊張は 2 体が指摘したが、どちらも「Kernel の中では示せていない」とした。検査どうしは矛盾できない（両方通るか、片方が落ちるかだけ）。Lean の `pred_disjoint` が使えるのは、両方が同じ型の述語になっているときだけ。

自然言語の決定どうしの矛盾は、いまのところ読んだ者が気づくかどうかに依存する。共有メモと同じ。

### 3.10 乗らない決定は、何が足りないかを言える

N10〜N12 で 3 体は一致して、閾値や時間や範囲を発明することを拒んだ。そのうえで足りないものを具体的に挙げている。

- N10: 「安全」と「有用な作業」の尺度、目標値、マージ結果のデータ
- N11: どのモジュールが「信頼の土台」か、「1 人で読める」の大きさ
- N12: 時間の上限、機械、ログの大きさ

これは決定を検査できる形にするために人が決めるべきことの一覧になっている。系が出せるのは判定ではなく、この問いのほう。

### 3.11 以前の実走から

- **閉じた命題に接続した自然言語の主張は 0.8 で止まる。** 証明が通っても、仕様の仮説（基準率 0.6）に証拠がないため（自己適用の試行、三角不等式）。同じ主張に性質テストを 1 件足すと 0.96 になり閾値を超えた。越えさせているのはカタログの仮置きの数字で、形式化の忠実さは誰も確かめていない。
- **不要な仮定が入る。** 三角不等式の形式化は「重みの和が 1」を仮定に置いたが、証明は使っていなかった。
- **言語の食い違い。** 文書が日本語、ワーカーの検索語が英語で、対応する記述を見つけられなかったことがある。
- **同じ文面は同じ主張になる。** 2 体が相談なしに一字一句同じ述語を書いたことがある（`clamp` / `bound`）。短く定型的な性質では起きる。

### 3.12 散文を「読む」ことは、事実の抜き出しなら安定している

`docs/spec.md`（日本語の散文と表）の 5 箇所について、互いに見えない 3 体に「この節が言っていること」を Lean の項として読ませた（`experiments/prose/RESULTS.md`）。許可される公理の一覧、数値 1 個、ツール名 14 個の表、状態名 6 個（日本語の語を英語の識別子に訳す必要がある）、既定値の名前 1 個。

- 15 個の読みはすべて同じ値になった（1 体が `14` を `(14 : Nat)` と書いた違いだけ）。
- 言い換えただけの編集のあと、読み直した項は同じだった。意味を変えた編集のあとは、変わった値を読んで、決定の否定を証明した。
- 読み直したエージェントは、頼まれていない矛盾にも気づいて報告した（§3 の既定値を変えたが、§2 の表は元のままになっている）。ただしこれは報告の文章の中だけで、Kernel には記録されていない。

§3.2〜3.5 の損失（弱める、すり替える、中身がなくなる）が出なかったのは、問いの形が違うから。あちらは「この文を命題にせよ」で、こちらは「この節は、決められた型の値として何と言っているか」。型と問いを人が決めた時点で、解釈の余地の大半が消えている。規範や条件を述べる散文（「〜すべき」「〜の場合は」）は試していない。

一方で、読みを支えるものは依然としてない。エージェントが述べただけの読みは 0.875 で閾値に届かず、人が確認すると 0.984 になり、節が変わって読み直すとまた 0.875 に戻る。散文の対象では、変更のたびに人の確認が要る。

## 4. 仕組みの側の整理

| 決定の種類 | Kernel での形 | 当て直し | 残る不確実性 |
|------------|---------------|---------|--------------|
| 人が述語で書いた決定 | 形式的な主張（`claim_formal`、述語は Γ） | モデルを付け直して無作為な検査を再実行。証明はそのまま使える | コードとモデルの対応。定義が意図どおりかは系の外 |
| ワーカーが Lean にした決定 | `claim` ＋ `ground_at` | 同上 | 上に加えて、文と述語の対応（仕様の仮説）。確かめる手段は空虚性の検査だけ |
| 検査にした決定 | `claim` ＋ 記録されたコマンド | コマンドを再実行（`pw.check`）。落ちれば失敗 | 検査が決定の一つの読み・一つの場面でしかないこと。数字には尤度としてしか現れない |
| 乗らない決定 | 入れても基準率のまま | できない | すべて |

## 5. 使い方の指針

1. **大事な決定は、人が述語で書く。** ワーカーに文を翻訳させると、弱められ、コードから切り離され、しかもそれが証明つきで通る。Γ の定義を人が書いて確認するのが、いま唯一、文と述語の対応に責任を持てる方法。
2. **ワーカーに形式化させるなら、コードに結びつけさせる。** コードについての決定を閉じた命題にさせない（`ground_at` を使わせる）。閉じた命題への接続は、コードを伴わない数学的な主張に限る。
3. **形式化の一致を、忠実さの証拠として数えない。** 少なくとも同じモデルの著者どうしでは。
4. **検査にした決定は、下界ではなく検査の通過で扱う。** `pw.check` はそうしている。検査が何を見ていないかは、著者の申告を読む。
5. **割れる決定は、決定のほうを直す。** N7 のように読みで結論が変わるものは、検査を選ぶ前に文を絞る。
6. **乗らない決定は、足りないものの一覧を受け取って人が決める。** 決めるまでは共有メモに置く。Kernel に入れても何も起きない。

## 7. この調査の限界

- 3 体は同じモデル。違うモデルの著者なら一致の意味は変わるが、試していない。
- 各 1 回の実行で、ばらつきは見ていない。
- 決定は 12 個で、選んだのはこのプロジェクトの設計者。Lean に乗る割合などの数字に一般性はない。
- 「どれが正しい形式化か」は誰も判定していない。忠実さについての記述は、文と形式化を読み比べた結果で、測定ではない。
