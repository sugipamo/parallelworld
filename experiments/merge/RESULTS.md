# 記録のマージ：2 つのブランチが両方とも記録を足したとき

記録（`pw-log.jsonl`）は追記式で、ブランチどうしは両方が足した行を両方残してマージする（`merge=union`）。複数のセッションが同時に動く使い方では、これが毎回起きる。マージ後の判定が、マージの向きによらず同じで、正しいかを確かめた。

```
python experiments/merge/run.py --out experiments/merge/results/merges.json
```

シナリオごとに、本物の git で小さなリポジトリを作る。土台のコミットから 2 本のブランチを切り、それぞれがファイルを変えて `pw.maintain` 相当の記録（計算した読み、等式、証明、目隠しの読み）を足す。a を b に、b を a に、両方の向きでマージして、事実を当て直す。記録は git の `merge=union` に任せ、ほかのファイルの衝突はシナリオが決めたとおりに解く。

| シナリオ | マージ後の判定 | 向きで同じ | 期待どおり |
|----------|----------------|-----------|-----------|
| それぞれが別の事実を、全部の箇所で変える | 両方 一致 | ○ | ○ |
| 両方が同じ箇所を読むだけ（2 つのセッションが maintain を回した） | 一致 | ○ | ○ |
| 片方が値を全部の箇所で変え、もう片方が古い値を述べる箇所を足す | **食い違い** | ○ | ○ |
| 両方が同じ値を別々に変え、衝突をファイルごとに別の側で解く | **食い違い** | ○ | ○ |
| 同じく、衝突を全部片側で解く | 一致 | ○ | ○ |
| 同じ文面を 2 人の読み手が違う値に読む | 係争 | ○ | ○ |
| 片方が事実の宣言をやめ、もう片方がそれを読み直す | 残った事実は一致 | ○ | ○ |
| 同じく、マージで事実を残すことにする | 一致 | ○ | ○ |
| 片方が問い（説明文）を変え、もう片方が文面を変える | 読み直し | ○ | ○ |
| 両方が同じ事実に箇所を足す（宣言ファイルが衝突） | 一致 | ○ | ○ |

- 10 シナリオとも、2 つの向きで判定が同じで、期待どおりだった。
- どのマージでも、記録の行は 1 行も失われず、記録にある証明は全部 Lean を通り直した。
- **git が衝突なしでマージしたのに中身が食い違う場合を、検査が捕まえる**（3 番目）。片方のブランチは知っている箇所を全部直し、もう片方は古い値を述べる箇所を新しく足す。テキストとしては重ならないので git は黙ってマージし、`pw.check` が食い違いを報告する。並行作業でこの仕組みに期待していたのはこれ。
- 衝突を雑に解いた場合（4 番目）も同じく食い違いとして出る。
- 片側で解いた場合（5 番目）、捨てた側のブランチの読みは、もう存在しない文面についてのものなので、使われないだけで害はない。
- 問いと文面が別々のブランチで変わった場合（9 番目）、どちらの読みも「新しい問いに対する新しい文面の読み」ではないので、読み直しになる。古い読みが流用されることはない。

## 限界

- シナリオは手で作った 10 個。値は自然数と文字列、箇所は 2〜4。
- 読み手は記録への書き込みで代用した（本物のエージェントは使っていない）。確かめたのは記録とマージの扱いで、読み手の質ではない。
- 3 本以上のブランチ、リベース、チェリーピックは試していない。
