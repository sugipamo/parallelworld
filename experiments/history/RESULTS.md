# 履歴の再生：使い続けると何が起きるか

仕様書 §6 の「長く使った結果はまだない」を、2 つのリポジトリの履歴を 1 コミットずつ再生して確かめた。

- `python experiments/history/run.py own`：このリポジトリ自身の履歴。各コミットを、そのコミット自身の `pw.check`・宣言・記録で確かめる（CI が言ったこと、言ったはずのこと）。
- `python experiments/history/run.py late --repo <miclow> --rev 79e0afa --read claude-opus-5-5`：miclow の履歴。いまの宣言を、宣言がなかった頃の全コミットに当てる（最初から宣言していたら何が出たか）。散文の箇所は、内容が未読のものが出るたびに目隠しの読み手に読ませた。
- 集計は `python experiments/history/summary.py`。生の結果は `results/`。

## このリポジトリ自身（宣言と検査を持つ 45 コミット）

| 範囲 | コミット | 通った | 通らなかった | 通らなかった理由（コミット数） |
|------|---------|--------|--------------|------------------------------|
| 全部 | 45 | 25 | 20 | 読み直しが要る 13、読みが規則を満たさない 9 |
| CI が回り始めてから | 35 | 25 | 10 | 読み直しが要る 5、読みが規則を満たさない 7 |
| 使われていなかった層を削ってから | 14 | 14 | 0 | — |

- **箇所どうしの食い違い（`violated`）で落ちたコミットは 1 つもない。** 通らなかった 20 コミットは、すべて保守の理由だった。
- 通らなかったコミットは 5 つの連なりになっていて、どれも「記録を足すコミット」で終わっている。文書や宣言を変えたコミットと、読みを記録したコミットが分かれる、という §6 の限界がそのまま出ている。連なりの長さは 13・1・2・2・2。最初の 13 は、CI を入れる前に仕組みそのものを作り替えていた時期。
- 最後の 14 コミットは全部通った。そのうち 11 コミットは、宣言した箇所のあるファイルに触れている。値が実際に変わったのは 1 回（規則に使える条件の一覧。コードと文書を同じコミットで直している）で、あとは箇所の追加・削除が 3 回。
- つまりこの期間、検査は「落ちなかった」。食い違いを作らなかったのか、作る前に手元で直したのかは、コミットの履歴からは分からない。

## miclow（宣言がなかった 79 コミットに、いまの宣言を当てる）

| 事実 | 全部の箇所が宣言どおりに読めるようになったコミット | 読めてからの状態（コミット数） |
|------|------------------------------------------------|------------------------------|
| license | 4 | 食い違い 76 |
| repository URL | 4 | 一致 76 |
| project_version | 8 | 一致 72 |
| Python client methods | 8 | 食い違い 72 |
| Python module-level functions | 8 | 食い違い 72 |
| system_commands | 54 | 食い違い 20、一致 6 |
| task configuration keys | 54 | 食い違い 26 |
| task_id_env_var | 59 | 一致 21 |

- **食い違いは、箇所ができた最初のコミットからあった。** 5 つの事実は、読めるようになった時点ですでに食い違っていて、4 つは最後まで続いた。最初から宣言していれば、初日から赤になり、直すまで赤のままだった。「後から入り込んだずれを捕まえる」形ではない。
- **片方だけが変わったコミットは 79 のうち 5 つ**（マージを除く）。`MiclowClient` のメソッドとモジュール直下の関数が、コードだけ 5 回変わり、文書は追随しなかった。うち 2 回はシステムコマンドの一覧も同じ。コードと文書が同じコミットで変わったのは 1 回だけ。検査があれば、この 5 回で止まっていた。
- 一度だけ、食い違いが解消している（74 番目、README から古い節を削ったコミット）。検査なしで直ったのはこの 1 件。
- **コードの置き場所が変わると、宣言は付け替えになる。** 3 つの事実は、54〜59 番目のコミット（モジュールの分割）より前には、いまの宣言では読めない。それより前に宣言していたら、この分割のところで `pw.discover` による付け替えが要った。79 コミットで 1 回。
- **散文の読み直しは少ない。** 79 コミットを通して、目隠しの読み手が新しく読んだのは 7 箇所（6 セッション、$0.24）。README の該当する節が変わったのは 5 コミットだけで、残りの版はいまの記録にある読みと同じ内容だった。読み手のセッションの失敗は 0。

## その後：Lean を通さずに比べても、判定は同じか

読み手の値を書き下した値に限ってから（`experiments/gate/RESULTS.md`）、比べるものはどれも数・文字列・その一覧になった。同じか違うかは見たとおりで、Lean に証明させる意味が薄い。Lean を通さずに比べるやり方に替える前に、同じ履歴を両方のやり方で再生して、判定を突き合わせた。

```
python experiments/history/run.py late --repo <miclow> --rev HEAD --lean needed --out a.json
python experiments/history/run.py late --repo <miclow> --rev HEAD --lean always --out b.json
python experiments/history/compare.py a.json b.json
```

| 履歴 | コミット | 事実ごとの判定 | 違い | 所要時間（そのまま比べる / 全部 Lean） |
|------|---------|---------------|------|--------------------------------------|
| miclow（いまの宣言を全コミットに） | 103 | 1,133 | 0 | 1 分 10 秒 / 2 分 36 秒 |
| このリポジトリ（各コミットの宣言と記録） | 23 | 204 | 0 | 19 秒 / 22 秒 |

- 状態、各箇所の読み、読みが成り立つかどうか、指示に反している箇所、全体にない要素。どれも 1 件も違わなかった。
- 既定を「そのまま比べる」に替えた。Lean に通すのは、定義された事実など、値を計算しないと決まらないときだけ。宣言に定義がないリポジトリ（miclow）は、Lean なしで確かめられる。

## その後：Rust で書き直した `check` は、同じ判定をするか

`check` を Rust で書き直した（`rust/`）。記録の中の識別子は文字列のハッシュで決まるので、箇所の切り出し方や読み方の書き表し方が 1 文字でも違えば、既存の読みが全部つながらなくなる。同じ履歴を両方の実装に通して突き合わせた。

```
python experiments/history/rust.py --repo <miclow> --rev HEAD        # いまの宣言と記録を、全コミットに
python experiments/history/rust.py --repo . --rev HEAD --own         # 各コミットが持っている宣言と記録で
```

比べたのは、事実ごとの状態、箇所ごとの読んだ値・成り立つかどうか・満たした規則・各条件の成否・数えられない読み手・指示に反する箇所・全体にない要素、読めない箇所の理由。

| 履歴 | コミット | 比べた判定 | 違い | Lean が要るので Rust 版の対象外 | 所要時間（Python / Rust） |
|------|---------|-----------|------|------------------------------|--------------------------|
| miclow | 103 | 1,133 | 0 | 0 | 157 秒 / 12 秒 |
| このリポジトリ | 45（宣言のあるもの） | 444 | 0 | 16 | 86 秒 / 7 秒 |

- 1,577 件の判定が、項目ごとに完全に一致した。途中で 1 つだけ違いが出た：古い書き方の宣言（箇所に知らないキーがある）を Python 版は断り、Rust 版は受け取っていた。Rust 版を同じ厳しさにした。
- その前に、箇所の識別子・読み方の書き表し・読んだ値だけを 3 つのリポジトリの 70 箇所で比べ、全部同じであることを確かめている（Python の構文木の切り出し、Markdown の節、JSON のキー、TOML の道筋を含む）。
- 表示（テキストの出力）も、miclow の通る場合と落ちる場合で 1 行ずつ同じ。違うのは、構文解析に失敗したときにライブラリが言う文言だけ。
- 「同じ宣言はどの実装でも同じ意味になる」という §2 の主張を、初めて 2 つの実装で確かめたことになる。

### Lean を呼ぶ部分も移したあと（0.11.0）

Rust 版が Lean を呼ぶようになった（定義のある事実、`--lean always`、`--verify`）。比べる項目に、事実の決まった値・定義が与える値・待っている事実・定義と違う箇所を足して、もう一度全部を通した。

```
python experiments/history/rust.py --repo <miclow> --rev HEAD                 # いまの宣言と記録を、全コミットに
python experiments/history/rust.py --repo <miclow> --rev HEAD --lean always   # どの比較も Lean に通して
python experiments/history/rust.py --repo . --rev HEAD                        # このリポジトリ（定義を 1 つ持つ）
python experiments/history/rust.py --repo . --rev HEAD --own
```

| 履歴 | 比べた判定 | 違い | 所要時間（Python / Rust） |
|------|-----------|------|--------------------------|
| miclow | 1,155 | 0 | 159 秒 / 11 秒 |
| miclow、`--lean always` | 1,155 | 0 | 371 秒 / 210 秒 |
| このリポジトリ、いまの宣言 | 890 | 0 | 165 秒 / 48 秒 |
| このリポジトリ、各コミットの宣言 | 470 | 0 | 86 秒 / 14 秒 |

- 3,670 件が項目ごとに一致した。以前は対象外だった、定義のある事実（このリポジトリの「規則が求めてよい条件の数」）も含む。
- Lean を通すと、時間のほとんどは Lean の実行そのもの（コミットごとに 1 回は型を確かめる）で、実装の差は縮まる。
- `--json` の出力は、このリポジトリで 1 バイトも違わない（各箇所の `question` を出し、キーの順とインデントを Python 版に合わせた。#11）。テキストの出力、`--verify` の出力、確かめられないときのエラー文も同じ。違うのは、JSON や Python を解くライブラリが言う文言だけ。

## 分かったこと

- 保守の手間は、主に「変更と記録が別のコミットになる」ことから来る。このリポジトリでは CI 導入後の 35 コミット中 10 コミットがそれで落ちた。層を削って仕組みが落ち着いてからの 14 コミットでは 0。
- 読み直しの費用は小さい（miclow の全履歴で $0.24）。
- 効き目のほうは、miclow では 79 コミット中 5 コミット（6%）で「片方だけ変わった」を止められた計算になる。ただし前提として、最初からあった食い違い 5 件を一度直しておく必要があった。
- リファクタリングで箇所が動くと宣言は読めなくなる（黙って別のものは読まない）。頻度は 79 コミットで 1 回。

## 限界

- miclow の再生は、最後の時点に合わせて書いた宣言を過去に当てている。過去のどこかで宣言を書いた場合に、その後どれだけ壊れたかは、この向きでは測れない（分かるのは「いつから読めるか」だけ）。
- このリポジトリ自身の履歴は、仕組みを作りながら使っていた時期を含む。落ちた理由の多くは、仕組みの作り替えそのもの。
- 2 つのリポジトリ、どちらも小さく、開発者は 1 人と少数のエージェント。
- 各コミットの判定は、そのコミットの木を単独で見ている。マージコミットの親の違いは数えていない。
