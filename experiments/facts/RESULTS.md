# 事実と箇所：このリポジトリ自身での実走

実行: `python -m experiments.facts.run OUT_DIR`（クローン上で回す）。生の結果は `results/result.json`、最初の実行は `results/result-first-run.json`。

## 設定

リポジトリ直下の `pw-facts.json` に、このプロジェクトの事実を 6 つ宣言した。事実は一つの事柄で、それを述べている箇所を全部挙げる。決定は「全部の箇所が同じ値として読める」。正解の値は決定に書いていない。

| 事実 | 型 | 文書の箇所（エージェントが読む） | コード・設定の箇所（変換式が読む） |
|------|----|----------------------------------|--------------------------------------|
| 既定の依存クラス | 文字列 | `docs/spec.md` の 3 節と 2 節、`docs/symbols.md` の 7 節 | `pw/kernel.py::Kernel.__init__` |
| 許可される公理 | 文字列のリスト | `docs/spec.md` の 5 節 | `pw/lean_gate.py::ALLOWED_AXIOMS` |
| 解ける連結成分の上限 | 自然数 | `docs/spec.md` の 7 節 | `pw/kernel.py::Kernel.__init__` |
| MCP ツールの名前 | 文字列のリスト | `docs/spec.md` の 4 節 | `pw/mcp_server.py` |
| 既定の閾値 | 自然数（千分率） | — | `pw/orchestrator.py`、`pw/check.py`、`pw/maintain.py` の `main` |
| Lean の版 | 文字列 | — | `lean/lean-toolchain`、`experiments/selfcheck/lean/lean-toolchain` |

回し方は 3 つのコマンド。

```
python -m pw.check       # 変換式の箇所を読み直し、箇所どうしを比べる。エージェントなし
python -m pw.maintain    # 加えて、変わった箇所・未読の箇所をエージェントに読ませる
python -m pw.confirm     # エージェントの読みを、根拠の一文と並べて人が確認する
```

## 結果

| 段階 | 何が起きたか | エージェント |
|------|--------------|--------------|
| 最初の `pw.check` | コードだけの事実 2 つは ok。文書を含む 4 つは「未読」 | なし |
| `pw.maintain` | 文書の 6 箇所を読み、どれもコード側と同じ値。ただし「誰も確認していない」ので FAIL | 12 手、$0.28、25 秒 |
| `pw.confirm` → `pw.check` | 6 つとも ok、終了コード 0 | なし |
| 仕様書の 3 節だけ既定値を変える | その箇所だけ失効 → 読み直すと `"frechet"`。**「箇所が同じことを言っていない」**（3 節は frechet、他の 3 箇所は pqd） | 5 手、$0.15、11 秒 |
| 残りの文書とコードを揃える | コードは機械的に読み直し。文書 2 箇所を読み直して一致。人が確認して ok、終了コード 0。**決定は書き直していない** | 6 手、$0.16、13 秒 |
| `pw/maintain.py` だけ既定の閾値を変える | 「箇所が同じことを言っていない」（900・900・800） | なし |

各 1 回の実行、エージェントは claude-opus-5-5。

## 読み取れること

- **前回、エージェントがたまたま気づいた食い違いが、機械的に出るようになった。** 散文の実験で「3 節を変えたのに 2 節は元のまま」と報告されたのと同じ状況を作ると、今度は箇所ごとの読みの一覧つきで報告された。
- **値を変えても、決定は書き直さなくてよい。** 全部の箇所を揃えれば一致に戻る。決定の側に正解を書いていないので。
- **コードどうしのずれは、エージェントなしで出る。**
- **この実走は、実際の作業の確認にもなった。** 今回 `read_place` というツールを足し、仕様書の表にも行を足した。エージェントが文書から読んだ 15 個の名前は、コードから機械的に抜き出した 15 個と一致した。
- **1 回の読み取りは 10〜25 秒、$0.15〜0.28。** 人の確認は、読みと根拠の一文を見比べるだけ。

## 最初の実行で見つかって直したこと

- **人が確認できなかった。** 確認の表示は節の先頭 600 字で、長い節では該当の文が見えなかった。読みに根拠の一文を付けさせ、それが節に一字一句あることを Kernel が確かめ、確認の表示にはその一文を出すようにした。
- **箇所が 4 つある事実が、全部確認しても通らなかった**（下界 0.852）。「全部の読みが同時に正しい」確率の下界は、箇所が増えるほど下がる（どれか一つが誤りうる）。判定は読みごとに行い、全体の区間は参考として出すようにした。
- **根拠の一文で読みを留める扱いを、一覧には使わないようにした。** 単一の値の読みは、根拠の一文が節に残っているかぎり有効とした（節の中の無関係な編集で読み直しにならない）。しかし一覧は箇所全体から読むもので、根拠は表の 1 行でしかない。行が足されても読み直されなくなるので、一覧は箇所の内容が変わったら読み直す。この修正は実走のあとに入れたもので、テストで確認している。

## 限界

- **事実と箇所の一覧は、人が書く。** どの事柄がどこに書いてあるかを挙げ漏らせば、その箇所は見られない。
- **変換式も人が書く。** 今回は正規表現で抜き出す式を私が書いた。式が正しいかどうかは、基準率 0.98 という仮置きの数字でしか表していない。
- **単一の値の読みは、根拠の一文が残っていれば有効のまま。** 同じ節の別の場所に、それと矛盾する文が足されても気づかない。
- **一覧の確認は、根拠の 1 行では足りない。** 人は節全体と見比べることになる。
- **散文の箇所は、変わるたびにエージェントの読み直しと人の確認が要る。**
- **（この実走の時点では）記録はリポジトリの外だった。** イベントログは git の管理外にあり、別の環境でクローンすると、エージェントの読みと人の確認は引き継がれなかった。その後、記録を `pw-log.jsonl` としてリポジトリに含める形に変えた（`docs/spec.md` §10）。
- **読ませたのは事実の抜き出しだけ。** 名前、数値、既定値。規範や条件を述べる散文は試していない。
