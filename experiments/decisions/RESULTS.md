# 過去の決定との矛盾を確認できるか

実行: `python -m experiments.decisions.run OUT_DIR`。生の結果は `results/result.json`。

## 設定

決定は「コード s は述語 P を満たす」という形式的な主張として記録する。述語は Γ の定義（`Spec.ValidIndex` など）。

1. **セッション1**: ワーカーが `clamp_index` を実装し、決定「結果は常に有効な添字」（`Spec.ValidIndex`）を確立する。ブランチをマージする。
2. **その後（言語モデルなし）**: マージ後のコードを手で3回書き換え、そのたびに `python -m pw.check` を実行する。
3. **セッション2**: 同じ関数について、新しい決定を2つ、別々のワーカーに渡す。一つは過去の決定と両立しない（範囲外なら n を返す）。もう一つは両立する（範囲内ならそのまま返す）。

各段階1回ずつ、ワーカーは claude-opus-5-5。

## 結果

### 変更と決定

| コードの状態 | `pw.check` | 下界 | 終了コード |
|--------------|-----------|------|-----------|
| マージ直後 | 再確立 | 0.996 | 0 |
| 挙動を保つ書き換え（`i if i < n else n - 1`） | 再確立 | 0.914 | 0 |
| 決定を破る変更（`min(i, n)`。テストも通るように弱めた） | **破れ** | 0.704 | 1 |
| 元に戻す | 現行 | 0.996 | 0 |

破れたときの報告:

```
FAIL broken  [0.704, 0.704] H:8bf20776cf indexing.py::clamp_index satisfies Spec.ValidIndex
     the code no longer matches the model the proof was about: on 12 7 the model gives 6, the code gives 7
```

- 書き換えのたびに、Kernel は同じ Lean のモデルを新しい版に付け直し、保存してあった無作為な検査を引き直して実行した。一致すれば以前の証明がそのまま有効、食い違えば反例つきで破れと判定する。
- 破る変更ではテストも弱めてあり、テストは通っている。検出したのはモデルとの突き合わせ。
- 挙動を保つ書き換えで下界が 0.914 に下がったのは、こちらの書き換えが「負の引数で例外を出す」挙動を落とし、セッション1のテストが1件失敗したため。自然数の範囲では挙動は同じで、判定は再確立のまま。
- マージ直後が「現行」でなく「再確立」なのは、ワーカーがモデルを付けた後にファイルをもう一度編集していたため。

### 決定と決定

| ワーカー | 新しい決定 | したこと | 手数 | 費用 |
|----------|-----------|----------|------|------|
| sentinel | 範囲外なら n を返す | 過去の決定と両立しないことを Lean で証明し、コードを変えずに止まった | 5 | $0.17 |
| identity | 範囲内ならそのまま返す | 既存のコードのまま確立。セッション1と同じ Lean のモデルを使った | 14 | $0.26 |

セッション2の後の `pw.check`:

```
ok   current      [0.998, 1.000] H:8bf20776cf indexing.py::clamp_index satisfies Spec.ValidIndex
FAIL unsupported  [0.000, 0.001] H:d3d2dad382 indexing.py::clamp_index satisfies Spec.OverflowSentinel
ok   current      [1.000, 1.000] H:c000d1173b indexing.py::clamp_index satisfies Spec.IdentityInRange
FAIL contradictory decisions about indexing.py::clamp_index: H:8bf20776cf (Spec.ValidIndex) and
     H:d3d2dad382 (Spec.OverflowSentinel) cannot both hold (verified by Lean)
```

人が新しい要求を取り下げる（`Kernel.withdraw`、理由つき）と、残る2つが `ok` になり終了コードは 0 に戻る。

表と出力にある「破れ」（`broken`）は、その後「証明の対象外」（`uncovered`）に名前を改めた。この実行では実際に決定の違反だったが、一般に分かるのは「コードが証明の対象だったモデルと一致しなくなった」ことまでで、違反とは限らない（`experiments/selfcheck/RESULTS.md` の追記）。

## この実行で見つかって直したこと

- **矛盾する提案が、同じコードについての主張を全部評価不能にしていた。** 確立済みの決定と両立しない提案は、基準率 0.5 に置けない。そのためオーケストレーターの判定が例外で落ち、無関係な3つ目の主張まで巻き込まれた。基準率を「それを排除する決定が成り立たない世界の中で」とるように直した。上の `pw.check` の出力は修正後のもので、ワーカーの実行はやり直していない。
- **同じ回に登録した主張が、互いに「過去の決定」として見えていた。** identity のワーカーは、まだ誰も確立していない sentinel を過去の決定として読んでいた。その回より前からあった決定だけを渡すように直した。

## 限界

- **矛盾を見つけるのはワーカー。** 決定どうしが両立しないことは、誰かが証明を試みて初めて記録される。Lean が保証するのは「記録された矛盾は本物」までで、「矛盾があれば必ず見つかる」ではない。
- **変更の検出は入力分布に依存する。** 無作為な検査で食い違いが出ない程度の稀な変更は、再確立と判定される。今回の変更は入力の半分近くで食い違うものだった。
- **再確立できるのは、モデルが変わらない変更だけ。** 挙動が意図して変わった場合は、誰かが新しいモデルを付けて証明し直す必要がある。
- **形式的な決定だけ。** 自然言語の決定（設計方針など）はこの仕組みに乗らない。
- **題材は今回も自然数の一行関数。** 各段階1回ずつの実行。

## 結論

「過去の決定との矛盾を確認する」は、この題材では両方の意味で動いた。コードの変更に対しては言語モデルなしで機械的に、新しい決定に対しては Lean の証明つきで検出でき、両立する変更と両立する決定では誤って止めなかった。
